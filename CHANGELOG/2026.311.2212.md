# 2026.311.2212 — docs(design): settle the two VM rows on what config: can and cannot carry

## Summary

Two owed rows of the capability ledger (`design/dulling.tsv`, tracked in #838), re-derived against the
CURRENT `DESIGN.md` and `DESIGN.cue` instead of against the cells as they were written. Both rows were
written when `#MachineFields` was `{from!, publish?}`; batch 58 (opencharly/opencharly#917) put
`config?: #Opaque` on it under D-HW-5's S10 exception, so **both cells opened with a claim that is now
false**, and a settlement cannot stand on a false premise:

```console
$ git show origin/main:design/dulling.tsv | awk -F'\t' '$1 ~ /^kind:(firecracker|kubevirt)$/ { print $1": "$6 }'
kind:firecracker: #MachineFields is `{from!, publish?}` and D-HW-5 `No candy, box or deployment carries raw runtime settings (... libvirt XML)` — the jailer, tap/cni network, containerd snapshotter, MMDS/vsock/console and snapshot knobs have no field, and the host surface has no node at all
kind:kubevirt: #MachineFields is `{from!, publish?}` and an inner `vm` body admits no KubeVirt field — the source arms, instancetype/preference, run_strategy, migration, snapshot and affinity have no home
```

What the exception actually reaches is a `pod`, `vm` or `agent` body, and what it may not carry is a
security option or a device path. Both rows therefore stay `dulled`, but on grounds that survive the
correction — and one of them was owed on the wrong requirement.

**`kind:firecracker` — the amendment it owes is now the real one, and the action changes.**

| today's surface | where it lands in the target design |
|---|---|
| MMDS, vsock, console, the machine type (`smt`, `huge_pages`, `cpu_template`) | `config:` on `#MachineFields` (D-HW-5/S10) |
| `image:` (from/format/disk_mib/resize) | the `from:` box or source, with the root drive's size a `need: storage: {root: …}` and the growth the `os`'s conversion (§14.2) |
| the guest `kernel:` (from/path/sha256/cmdline/initrd) | the `os`'s `boot` content (§16.4, `#Boot`); the row `Firecracker rootfs + kernel` already settled this |
| `machine.vcpu_count` / `mem_size_mib` | `need: cpu: {core: …}` and `need: memory: {ram: …}` |
| `cloud_init:` | the box (§16.4) |
| `snapshot:` (create/mem_file_path/snapshot_path/snapshot_type/resume) | D-CAPTURE-5's trade, recorded in §A.9 (`capture` is the one way back) |
| **the HOST side** — the VMM pin with its `jailer`, `containerd.snapshotter` with its devmapper `device`, the `tap`/`cni` path with `forwarding`, the `fireactions` pool | **nowhere.** `config:` reaches a `pod`/`vm`/`agent` body and nothing else, D-HW-5 bars a security option (the jailer) and a device path (the devmapper device) even there, D-DRV-1 makes a driver *a row, never a kind* (so `kind:firecracker`'s host block cannot survive as a kind), and D-DRV-3 has a row declare what a driver **gives** and says nothing about the host surface it needs |
| the extra `drives:` and the `rate_limits:` | raw runtime settings and a device path, barred by D-HW-5 |

The action moves from `amend D-DEP-1` — pod-and-vm symmetry, which has nothing to do with a host — to
`amend D-DRV-3`, and the row's `guideline` now names D-DRV-3 as governing it (until now the row's action
named a requirement its own `guideline` did not).

**`kind:kubevirt` — the amendment is much smaller than the cell claimed.**

| item | where it lands |
|---|---|
| `instancetype` / `preference` | `config:` — D-HW-5 names *an instancetype* explicitly; `#ClusterKubeVirt` carries `default_instancetype`/`default_preference` for the cluster |
| `machine: q35\|pc-i440fx`, `firmware:` (bootloader/efi_secure_boot) | `config:` — D-HW-5 names *a firmware* explicitly |
| `run_strategy` / `eviction_strategy` / `termination_grace_period_seconds` | `config:` (the vehicle's own spec: not a grant, not a size, not a security option, not a device path) |
| `cluster` / `namespace` / `storage_class` / `kube_context` | the `kubernetes` body it is written inside (`#KubernetesFields`, `#ClusterStorage`, `#ClusterKubeVirt`) |
| `source.kind: container_disk` | the `oci` arm of `#SourceAlt` (the image plus the `os` boot content, converted to a disk, §14.2) |
| `source.kind: data_volume` (a CDI import) | its `http`/`registry` arms are `disk: {url, sha256}` or `oci`; a `blank` volume is a `storage: {root: …}` need beside the source that fills it; importing FROM a claim is the `pvc` case below |
| `source.kind: clone` | a capture — `from:` a deployment is a capture (§14.1, §17.3) |
| live migration, DataVolume import | §A.9's row: READ with the `kube` verb's `resource` operation, never an operation of their own |
| `snapshot:` (name/description/snapshot_class) | a capture (D-CAPTURE-5), with the class from `#ClusterKubeVirt.volume_snapshot` |
| **`source.kind: pvc`** — a disk the cluster already holds | **nowhere**: `#SourceAlt` is `oci`/`disk` (`url`+`sha256`)/`iso`/`bootstrap` plus a capture of a deployment, and every arm names an `os` a bare claim has none of |
| **`node_selector` / `affinity`** | **nowhere**: `#ClusterPodDefault` is the CLUSTER's policy ("when the workload names no selector") over a `pod`/`vm` body that carries no selector of its own |

No vocabulary was invented to turn either row green: `kind:firecracker` and `kind:kubevirt` are not kinds
the closed first-party kind set has (D-KIND-1), a KubeVirt guest is a `vm` inside a `kubernetes` body,
and both rows keep `dulled` with an amendment named for the part `config:` cannot reach.

**Two stale references are corrected with the row that settles them.** Both `#ClusterKubeVirt` comments
called its consumer *a `kind:kubevirt` target* — a kind the design's closed kind set does not have
(D-KIND-1), and the same claim this row's `target_form` falsifies. And the two rows' spec citations now
bound their definitions whole: `#Firecracker` is 35–61 (was 35–60) and `#KubeVirt` is 18–77 (was 18–75,
which ended on the `migration:` line and so skipped `snapshot:` and the closing brace).
