# 2026.242.1055 — docs(pi): document verified total-cap semantics and answer-room constraint

## Summary

Adds the probe-verified semantics to the root-cause section in `.pi/APPEND_SYSTEM.md` (PR #55 established the 65536 cap; this PR documents how it behaves):

- **`max_tokens` is the TOTAL cap** (thinking + answer), not the answer budget. Proven by `pi -p` probes: `maxTokens=49152` truncated at exactly 49152 output tokens; `maxTokens=65536` at exactly 65536. The "maxTokens = 65536 - thinking" formula is therefore wrong for this provider — it reduces total room and truncates sooner. (It would be correct for Anthropic-style providers where max_tokens is the answer budget.)
- **The thinking budget (16384 for high) is not hard-enforced**: a probe generated ~60K thinking against it, leaving ~5K for the answer. The harness's `resolveClampedThinkingBudget` clamps thinking to leave only 1024 answer tokens — the design gap.
- **Practical constraint**: with high thinking, the answer room is ~5K tokens (~20K chars). Tool calls must stay under that; heavy work must be delegated to subagents.

## How tested

- **Live probes (`pi -p`, 2026-08-30):** `maxTokens=49152` → session log shows `"output":49152` + `stopReason:"length"` (truncated at exactly 49152). `maxTokens=65536` → `"output":65536` + `stopReason:"length"`. Probe 3 (long tool call) → ~60K thinking against the 16384 budget.
