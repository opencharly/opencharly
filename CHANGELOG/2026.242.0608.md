# 2026.242.0608 — fix(pi): break the output-token-limit retry loop with a loop-guard extension

## Summary
The pi agent looped for hours generating hundreds of IDENTICAL tool calls, each rejected with "the response hit the output token limit, so its arguments may be truncated" (600M+ tokens burned, zero progress).

**RCA (8-step):** when the model's response exceeds the output token cap, the pi harness (`runLoop` → `failToolCallsFromTruncatedMessage`) rejects every tool call in the truncated message with the error *"Re-issue the tool call with complete arguments"* and returns `terminate: false`. That error message INSTRUCTS the model to re-issue the same call; the model regenerates the same oversized response; it is truncated again; the loop repeats forever. The truncated path bypasses the `tool_call`/`tool_result` extension events, so the loop cannot be intercepted at the rejection — but the RETRY goes through the normal path.

**Fix (root, not workaround):** a new project extension `.pi/extensions/loop-guard.ts` that:
1. On `message_end` with `stopReason === "length"` (truncated response), records the tool calls the truncated message carried.
2. On `tool_call`, when a call matches a recorded truncated call (same tool + same args), BLOCKS it with a corrective directive: do NOT re-issue — make a SHORTER response, split the work, or delegate to a subagent.

This changes the actual instruction that drives the loop (the harness's "Re-issue the tool call") into one that breaks it, at the exact point where the loop repeats. Plus `.pi/APPEND_SYSTEM.md` carries the behavioral discipline (short calls, minimal responses, subagents for exploration, never retry a truncated call).
