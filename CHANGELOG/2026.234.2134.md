# 2026.234.2134 — ci: tag-on-merge via push-to-main (replace dead closed trigger + flaky cron)

## Summary

Replaces the tag-on-merge triggers with a proper event-driven implementation. The dispatcher now fires on **`push` to `main`** — the event that IS the squash-merge — instead of relying on a dead `pull_request: closed` trigger and GitHub's best-effort cron.

**Full RCA — why tag delivery was irregular (8 steps):**

1. **Expected:** every merged PR gets a CalVer tag + CHANGELOG promptly (`pull_request: closed` fires at merge; `*/15` cron is a backstop).
2. **Actual (measured):** 17 consecutive cron runs delivered with intervals of 39, 25, 32, 28, 31, 27, 36, 26, 36, 22, 44, 25, 29, 21, 35, 28 min — **never once on the 15-min grid** (avg ~30). PR #3's tag landed **4+ hours late**; PR #7's tag (`v2026.234.2108`) was still missing 30+ min after the 21:08:33Z merge. **Zero `pull_request`-event runs in the workflow's entire history** (API-confirmed, 4 merges since the trigger was added in PR #4). The earlier `workflow_run` design died **15× in a row with `startup_failure`** (~12:12–12:51Z).
3. **Mechanism:** GitHub Actions cron delivery is best-effort with no SLA ("schedule events can be delayed during high load" — documented; this org runs heavy AI validator workflows). The `closed` trigger never created a run in this repo. The `workflow_run` attempt failed at startup (workflow-file issue). **The `push` trigger demonstrably fires** — verify.yml's push run landed **21s after PR #6's merge push** (17:36:30 → 17:36:51).
4. **Missed control:** the dispatcher's trigger selection. The org's *reusable* tag-on-merge logic is correct and idempotent; the failure was entirely in which event the umbrella's dispatcher listened for.
5. **Blast radius:** every merged PR (here and in every repo carrying this dispatcher) got tag+CHANGELOG 20 min–4+ h late; under worse cron load, tags would be skipped indefinitely — a defect per the rulebook.
6. **Root cause:** the only functioning trigger was GitHub's unreliable cron; the deterministic merge-time event — the `push` to main — was never used.
7. **Root fix:** trigger on `push: branches: [main]` (this PR). Event-driven, ~20s latency (proven), no cron, no dead closed-event dependence. The reusable sweep is idempotent — the CHANGELOG bot's own push re-triggers a cheap no-op sweep.
8. **Documented:** this body is the record; the file header carries the trigger-selection rationale.

**Self-validation on merge:** when this PR merges, the new push trigger fires tag-on-merge immediately, which will **backfill PR #7's missing tag `v2026.234.2108` + `CHANGELOG/2026.234.2108.md`** in the same sweep that tags this PR — an end-to-end live proof of the fix.
