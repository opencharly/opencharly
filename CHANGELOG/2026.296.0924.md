### Why the three surfaces move in ONE commit

`charly task org-map` verifies the README's org-map tables against `.gitmodules`: it requires every
submodule to have a row, every section to be sorted, and each section header's count to match. A row
removal alone therefore cannot make it green, and a gitlink removal alone leaves the gate red — the same
shape `#610` recorded. So the gitlink, the stanza, the row, the candy-layers section count (`20`→`19`)
and the repo total (`430 today`→`429 today`) are one change.

### What this PR deliberately does NOT do

- **No pin advance.** This is a removal, not a bump, so `charly task sync` was not run: its bump mode
  rolls every submodule not in `pin_map` and would carry other units' pins into a PR this scope does not
  own (Part II #3). Nothing was hand-pinned either.
- **No marketplace refs change.** The corpus refs list still pins `layer-charly-build:v2026.292.2017`;
  that is the switchover leg's own PR, whose proof is `diff -rq` of two generated corpora. Removing a
  gitlink changes no published byte, so this PR is corpus-neutral by construction. Measured on the
  pinned target: an ARCHIVED repo's tag is still fetchable
  (`git ls-remote https://github.com/opencharly/layer-charly-ollama.git 'refs/tags/v2026.295.2026'` →
  `23c00c7f…`, rc=0), so a pinned tag survives archival and the switchover can land afterwards without a
  window in which the corpus cannot resolve a source.
- **No archival in this PR.** The repository is archived after this merge and after its retirement
  notice (`layer-charly-build#33`) merges, so `tag-on-merge` can still mint that repo's final tag.
- **`layer-charly-internals` untouched** — the other carrier's skills are another leg's scope.
