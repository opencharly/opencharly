# 2026.309.1037 — docs(containerd-images): stop requiring an amdgpu-virtio mesa the distro does not ship

`CONTAINERD-IMAGES.md` §2's `pod-crabbox-gpu` row required, for DRM native context, "a mesa that carries amdgpu-virtio". No Arch/CachyOS package provides it, so the row stated a requirement the image cannot meet with named packages. This corrects the row to say what the image actually provides and names the gap with the measurement that establishes it.

## Summary

The measurement, from the issue and re-stated in the corrected row:

```console
$ pacman -Ss amdgpu-virtio
(no output)
$ pacman -Ss amdgpu_virtio
(no output)
$ pacman -Ss vulkan-radeon
extra/vulkan-radeon 1:26.2.5-1
    Open-source Vulkan driver for AMD GPUs
```

`vulkan-radeon` is the host-side RADV driver, not a guest `amdgpu-virtio` ICD. So there is no named package to satisfy the row.

The row now says the image provides the **Venus ICD** (`vulkan-virtio`), the **software fallback** (`vulkan-swrast`) and `vulkan-tools`, and states explicitly that **DRM native context (`amdgpu-virtio`) is not provided** — with the reason, and with the note that delivering it needs a **source-built mesa variant**, tracked in `opencharly/pod-crabbox-gpu#2`.

This matches what the image repo already does. Its own `charly.yml` states the same three packages and says the `amdgpu-virtio` variant "is NOT available as a named package in the CachyOS/Arch repos and is not claimed here", and `candy/gpu-vulkan/charly.yml` installs exactly:

```yaml
                package:
                    - mesa
                    - vulkan-icd-loader
                    - vulkan-virtio
                    - vulkan-swrast
                    - vulkan-tools
```

So the image never claimed native context; the specification was the side that over-promised.
