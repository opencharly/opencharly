# 2026.300.1232 — fix(pins): a REMOVED path renders a (removed) row, not a false divergence (#666)

Closes #666

## Summary

Head `7215132ef9258e43800b3ab5b7de2fdf74f0728e` — the commit this PR pushes: **3 files changed, 274 insertions(+), 43 deletions(-)**.

The umbrella's wave PR body is generated by two committed builders. The evidence table one of them builds compared a path this diff **DELETES** against that path's remote default-branch HEAD and flagged the row `!` — a false finding that reads exactly like a pin that is off its remote. A removal and a divergence are different facts, and the row must be able to tell them apart.

Measured on `origin/main` (2026-10-27), on a fixture whose `HEAD` records a gitlink the index no longer does, with the remote's default branch one commit ahead:

```
  sub  00f95b3fbbcb  006ddb64b729  !
```

**Mechanism.** The body is generated AFTER `git add -A` and BEFORE the commit, so a deletion is STAGED-but-not-COMMITTED: the index records no entry for the deleted path and `HEAD` still does. `staged_gitlink` fell back to `HEAD` for that path, and the render loop then compared the DELETED pin against the remote. The classification was never wrong — `is_gitlink_path` reads the same two places and answers `160000` correctly — only the row's VALUE was.

**The root fix** names the third state and puts ONE pair of readers underneath every classification:

- `index_entry` / `head_entry` — the index's and `HEAD`'s own record for a path, read with `git ls-files -s` and `git ls-tree HEAD`. `is_gitlink_path` and `staged_gitlink` are both expressed in terms of them, so a path's classification is ONE measurement of the index rather than several that can disagree.
- `is_removed_path` — true when the index records no entry for a path while `HEAD` still records one: this diff DELETES the path.
- `removed_row` — the row for such a path: `  <path>  (removed)`, naming the path and carrying NO `=`/`!` flag, because there is no staged pin to compare against a remote.

A removed GITLINK still changes the index's gitlinks — one of the pin check's three commit-carried inputs — so it stays in the gitlink-path set the coverage decision reads, exactly as the commit gate reads it (`:160000 000000` is a gitlink path there too). The coverage decision is therefore unchanged: the same fixture still reports "this diff changes 1 of them" before and after.

The body builder is cut over with it, because a body that counted a deletion as a move would be false in a new way: the summary now counts removals apart from moved pins, the changed-path section names the removed shape, and the change class is derived from the three counts, so it cannot describe a diff the table does not show.

**The retired MECHANISM claim is keyed, not only deleted.** The legend stated how the row's value was obtained — *"the STAGED GITLINK this PR records (`git rev-parse --verify --quiet :<path>` from the index, `git ls-tree HEAD` fallback)"* — and that read is gone, so the claim about the product's own mechanism is now false. A sweep written in a PR body is not a control: nothing in the repository runs it, so the claim comes back with the next legend that gets copied forward. The umbrella's own committed key set (`scripts/check-retired-claims.mjs`) is where a retired claim class lives, so the class is keyed there — with the instances that wrote it, the counter-instances that keep it sound, and the self-test arms that prove both.

**The missed control, named.** The self-test exercised `staged_gitlink`'s `HEAD` fallback, but never what the BODY does with the value that fallback hands it; and the retired form survived in the tree precisely because no key covered it. The new arms run the live body mode on a fixture whose `HEAD` records a gitlink and whose index does not, and assert the row it produces; the new class is RED on the pre-fix tree.
