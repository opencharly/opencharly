# 2026.281.1121 — docs(AGENTS)!: make the repo class and its naming rule a first-class contract

## Summary

Every repo's **name carries its class**, and the class decides what that repo may hold. Until now that rule lived only as an unwritten habit plus the README's grouping — and this cutover broke it: `opencharly/openclaw` was created as a product family with a **bare** name, and was renamed to `layer-openclaw` when the contradiction surfaced. The contradiction was in the draft contract itself: its class table named `layer-agentteams` (prefixed) as the canonical example of the very class whose repo name it called "bare". This lands the rule as a contract so the next session cannot repeat it.

- **`AGENTS.md`** — a new **Repo classes and naming** section in Part I: the gist only. The naming rule (bare names for core/contract and appliances **only**; every other repo carries its class prefix; a product family is a `layer-<family>` repo, never a bare name), the corrected example, and the pointers to the HOW.
- **`README.md`** ("The org map") — **one placement line per class**: the nine classes and what belongs in each, in the section a reader of the org map already opens. The rule those placements follow is *not* restated here; the paragraph points at the rulebook instead, so each statement has exactly one home.

**No new machine check is added, deliberately.** The contract says a machine check only where it can be false-positive-free, and one already owns this artifact: `charly task org-map` re-verifies that the org map reconciles, is sorted, and that every submodule has a row. To be exact about its reach, because it matters: this diff adds **placement prose above** the tables rather than table rows, so the verifier does not exercise the new sentences — it confirms the map still reconciles **with them present**, which is the property a placement line can break. It is cited in its **installed** form, because a repo-relative `./charly/bin/charly` path is not something a reader with only the installed binary can run.

## How tested

Every command below was executed **in this worktree**, with the worktree-local `2026.279.2047` binary — including the gate, which required initializing this worktree's own `charly/` submodule first. That worktree-specific detail is documented below with the isolation experiment that pinned it down, because it is a defect worth knowing about: a freshly created session worktree cannot load the project at all until that submodule is present.

**The session-worktree load cycle, and why the commit needed a completed checkout.** The commit's first attempt was refused by `hooks/pre-commit`, whose gate is `charly task policy-b` (`verb:git-submodules verify`):

```
$ charly task policy-b          # in a fresh session worktree
charly: error: command "task": load project: json: unsupported value: encountered a cycle via map[string]*spec.UnifiedFile
```

A throwaway `git worktree add --detach origin/main` fails **identically**, so it is the worktree state rather than this worktree; the main clone loads the same project fine (`task map` passes there). One controlled change isolated the trigger:

```
$ git submodule update --init --depth 1 charly     # in that throwaway worktree
[exit 0]        # charly/ now holds 17 entries

$ charly task policy-b
  [pass] check — policy B holds
```

**Mechanism:** charly's project loader needs the `charly/` submodule tree; `git worktree add` never initializes it, and with the gitlink un-initialized the loader mis-resolves the project and builds a self-referential `map[string]*spec.UnifiedFile`, so `json.Marshal` fails on a cycle before the verb can report anything. Initializing `charly/` **completes the checkout rather than bypassing the gate** — the hook still ran, and it passed:

```
$ git commit -F <msg>
pre-commit: OK
```

That is the full gate transcript the hook produced, and no bypass flag, hooksPath change or manufactured clone was used. The loader fix itself belongs to charly (its owning repo) and is routed as **W13 — session-worktree load hardening** in this cutover's ledger, together with the guidance gap that nothing says a session worktree must initialize `charly/`. (That is a different batch from **W12**, the plugin-call watchdog hardening this cutover also records; both are charly-owned and neither is worked around here.)
