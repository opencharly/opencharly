# 2026.312.1054 — feat(design): a flow that asks can be answered, and a schedule that is declared can be fired

## Summary

The operator ruled that the two holes the capability ledger's last owed rows name are a **contract change, not a retirement**: *"Build the amendment — the design gets an approval channel and a schedule runner."* This is that amendment (tracking issue opencharly/opencharly#838). A flow that asks can now be answered, a run can wait for the answer in `paused`, and a `schedule:` an author declares now has a named firing.

### The answer channel, and the vocabulary it reuses

`#StageAsk` was `{prompt!}` — a question with no channel, while `charly pipeline resume <entity>` answers a gate with `--approve yes|no`, `--cancel` or `--response-json J` that the design never formed. An ask now carries `answer!: #Answer`, and the whole stage table is the boundary that matters:

`expect:` is the response contract, and it is the **existing** `#Matcher` — exactly one comparison, with `not:` and `json:` composing it (D-VERB-3) — so a JSON response is asserted as `{json: {path: ".approved", match: {equals: true}}}` rather than by a second response schema. `unanswered:` is the outcome that applies when nobody answers, and it defaults to `refused`, so a gate nobody answers fails closed. The outcome words are a small table in the shape `_onError` already uses:

```text

["granted", "refused", "cancelled"]
rc=0
```

`expect`, `unanswered` and `answer` are the new authored fields; the example below fills all three in, and the negative case at the end leaves `answer` out.

### `paused` is observed, never commanded

`_state` gains `paused`, the word for a run waiting for its ask's answer. The `target` flag is the whole question, because `_targetStateWord` derives from it and `#TransitionInput.to` is built from that list: a target-bearing `paused` would make "pause this run" a command a document can issue, and it is not one — a run is paused by asking and leaves `paused` by answering. ### The schedule fires the one runner

§15.1 said "`charly pipeline run <name>` runs one; there is no second runner" — true, and it left `#Pipeline.schedule` a field nothing fired. The same sentence now carries the clause: the one runner is what a due `cron:` starts, and the schedule's own maintenance — install, list, remove, fire early — is `charly pipeline schedule …`, CLI maintenance over the pipeline the project declares, never an authored word and never a second engine.
