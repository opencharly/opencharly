**`kind:jetkvm` — the settings have a home: the project keeps the venue, the operator keeps the
device's own records.**

The cell's clause is true — a `local` node carries no `insecure:` and no `installer:` — but the
conclusion drawn from it (no field on the node, so no home at all) is not. The design has a home
for a plugin's own settings and for an operation a plugin owns, and the row now says so.

| today's surface (`#JetkvmDeviceInput` / `#JetkvmInstaller`, plugin pin `7e0dea3`) | where it lands |
|---|---|
| `host` — the device address | `#VenueKvm.address`: the venue a `local:` node's `connect:` writes — §17.7's own `lab-workstation` example is exactly this |
| `password_secret` — the credential-store key | `#VenueKvm`'s `secret`, through `#SecretFields` |
| `description` | the node's `description` |
| `insecure` — permit the device's self-signed certificate | **not the document's**: D-HW-5 bars a security option from every authored body, and the `config:` it allows reaches a `pod`/`vm` body (`#MachineFields`) and an `agent` (`#AgentFields`), never a `local` one (`#LocalFields`) |
| `installer` — named console recipes with `answers` / `answer_secrets` / `answers_env` substitution | the **plugin's own records**: `#UserConfig.section`, "each plugin's own section, under its own schema" (D-STORE-2, S10) |
| the install itself (it drives keyboard input over a recipe) | the plugin's own namespaced word (D-PLUG-7), never a verb: a state change is a field or a `run:` step (D-VERB-1) |

That is a narrowing the document states rather than an unowned gap, so `kind:jetkvm` keeps

The governing rules, quoted from the tree rather than paraphrased:

```console
$ grep -nE '^\| D-(VENUE-2|HW-5|STORE-2|PLUG-7|VERB-1|FLOW-1|FLOW-2) \|' DESIGN.md
557:| D-PLUG-7 | A word of a plugin outside the first-party set — kind, verb, command, type or api — is written under the namespace its project binds the plugin to (`strata.status`, `qdrant.collection`), so it never shadows a first-party word. |
810:| D-HW-5 | No candy, box or deployment carries raw runtime settings (capability lists, security options, device paths, libvirt XML); a grant that no host capability type expresses is added as a new type by its plugin. **One exception, and it is S10's.** A `pod` or `vm` body may carry `config:` — the one open field, whose fields the OWNING driver's plugin defines and this document never types — holding only what the vehicle's own shape needs and no grant expresses (a domain definition, a machine type, an instancetype, a firmware). A `config:` never names a driver (D-DRV-2), never restates a grant or a size (D-HW-4), and never carries a capability list, a security option or a device path, which stay needs and capability types. Two consequences are deliberate, not oversights: because D-DRV-2 keeps the driver out of the document, `config:` is validated against the BOUND driver row's schema before anything is realized and fails naming that driver when its row declares none — so this check happens at preflight rather than at authoring time as D-IR-6 otherwise requires; and a document that carries `config:` is portable only across drivers whose rows declare a config schema, which narrows D-DRV-2's "a box runs unchanged under every driver of its kind" to payload-free documents. |
1331:| D-FLOW-1 | A pipeline is a named set of stages run in the host venue, ordered by `after:`. A stage does exactly one thing (`#StageAlt`) — runs steps, runs another pipeline, realizes deployments and runs their checks, or asks the operator — and may run once per item of the list a parameter holds (`lane:`), with at most `concurrency:` lanes or deployments at once. A stage's steps observe the host venue, so their checks are deployment checks (§16.5). A pipeline's parameters are its needs and uses (§8). A stage's condition is a matcher per parameter (`when:`), never an expression; a gate over deployments, an agent loop over a run and an approval are stages, never fields of their own. |
1332:| D-FLOW-2 | A stage's `attempt:` is a declared, bounded count and the only repetition of a stage; it never repeats a failed plugin call (D-PROTO-7) and is never blind (D-LAW-5). |
2231:| D-VENUE-2 | A venue declares the accesses it serves (`#VenueFields`). An access it lacks — a microVM venue serves no `exec` — is refused naming the venue, never emulated, and a step that needs it is a load error (D-VAL-12). |
2433:| D-STORE-2 | The user configuration (`#UserConfig`) holds only what the user sets — one driver per subsystem (D-DRV-1), the leasable host resources (D-HW-4), image registry, the project-less `plugin:` list, whether the OS packages a plugin needs may be installed on the host (D-STORE-9), and each plugin's own section — under its own schema. |
2572:| D-VERB-1 | A verb observes and never changes state: a state change is a field (§14.4), and the one step that changes state is a `run:` step (D-VERB-5). Which verbs exist is D-VERB-6. |
```
