## Summary

Closes #1239. This follows #1237, at the operator's direction.

### 1. `package:` is a list of names, so no entry needs an empty `{}`

`#PackageMap` required a mapping per entry, so a plain package had to be written `ripgrep: {}`. A bare YAML key is null, and the schema rejected it. DESIGN.cue now has:

```cue
#PackageSet: [...(#Package | #ManagedPackage)] & list.UniqueItems() // D-CANDY-2: names, never a map
#ManagedPackage: {name!: #ManagerLocator, #ManagerPackage...}
```

- **The new form.** An OS or manager package is a bare name. A manager package that carries its manager's config is `{name, config}`. `#Content.package` and `#SourceBootstrap.package` use it.
- **S5 (named collection)** now names package names as plain values, which may sit in a list; its example of an empty entry is now `user: {app: {}}`. D-IR-7 cites `#PackageSet`.
- **Every content `package:` example in DESIGN.md is a list.** That is 16 flow maps, plus the helm example, which becomes `- name: … / config: …`.
- **The 21 negatives that used the map form** use the list form now. `manager-attributes-as-core-fields` (D-IR-5) and `package-input-os-package` (D-IR-6) are rewritten to the list shape, and each still fails for its own reason. A new negative, `package-as-map` (D-CANDY-2), proves that the old map is rejected.
- **The ledger snippets** in `design/parity.tsv` and `design/dulling.tsv` follow.

### 2. `package:` or `require:` — when to write which

A new §16.1 section, "`package:` or `require:`", states the rule, and D-CANDY-2 carries it:

- **`package:`** installs packages and nothing else. It is right when the package is the whole concern: one name everywhere, no file, service or user of its own, and nothing else needs it.
- **`require:`** composes a candy with everything it carries. It is right once the concern is more than a package name (configuration, a service, a per-OS name), or when several nodes need it.

A new example, `require-or-package`, shows both fields in one box. The `require` and `package` rows of the §16.1 table say the same. GRIEVANCES.md §1 gets the same section, "When to write `package:`, and when `require:`".

### 3. Check steps are optional

D-VAL-1 is rewritten rather than deleted, because deleting it would renumber every later D-VAL id, and other repos cite those ids. It now states: "A `check:` step is optional: a candy with content and no check is valid, and no loader, validator or build rejects it for having none." Its design-check column becomes `—`.

- **Removed in this change:** the D-VAL-1 check in `design/example/rules.cue`, its now-unused `_noContent` table, and the negative `candy-without-check.yaml`.
- **AGENTS.md:** the ADE rule no longer requires "at least one deterministic `check:`".
- **Check steps removed from examples, because they are no longer required.** There are seven, each the only check its node carried:
  - **DESIGN.md §17.4, `sandbox-box`:** "the container engine and the hypervisor are installed". #1237 added this step only to satisfy the old D-VAL-1; the example is about nesting, not checks.
  - **`design/negative/package-input-os-package.yaml`:** "ripgrep runs". It existed only so the case passed D-VAL-1; the case now isolates D-IR-6 alone.
  - **GRIEVANCES.md, five steps:**
    - §2: "ripgrep runs", "the system Python imports pyatspi" and "the NVIDIA user space is installed" (the last two went with the two `os_override` examples that §2 now replaces with one);
    - §4: "the container engine and the hypervisor are installed" and "the innermost container runs CachyOS".

    §5's four checks stay.
- **DESIGN.md's "7. Prove it."** now cites D-VAL-1 as "the plugin candy's checks are its acceptance".

### 4. GRIEVANCES.md

- §1's status quo is prose, with no table.
- §1's example shows `require:` and `package:` side by side. The `devtool.ripgrep` candy is gone, because ripgrep is one package with one name.
- §1 explains when to use which.
- §2 shows `os_override:` once, for one package (`python-gobject`), and refers back to §1 for the same-name case instead of repeating it.
- Only the examples in §5 carry check steps, and §5 says checks are optional.
- Every `package:` is a block list.
