# 2026.311.2119 — docs(design): a KubeVirt guest has no operation of its own

## Summary

Two owed rows of the capability ledger (`design/dulling.tsv`, tracked in #838), settled by the rules
the ledger already names — **both are a narrowing the design already decided, not a gap it owes**.

**`deploy:kubevirt` — the `amend D-ROLE-1` was owed on a false premise.** The row's `dulling` cell said
*§4.2's method list has no `migrate` or DataVolume-import operation*. `migrate` **is** a method of the
`kind` role: it is the schema reshape D-SCH-5 describes (`charly migrate` rewrites a body through the
owning kind's `migrate`), and that is exactly why a guest's migration cannot carry that name. What
survives the correction is the true half — live migration and DataVolume import are state-changing
operations of their own, a verb observes and never changes state (D-VERB-1), §23's verb table gives the
cluster `kube` and nothing else, and D-ROLE-1 makes the method table the whole plugin contract, so no
amendment is owed.

**`kubevirt create|…|migrate|gpu` — the `amend D-VERB-1` was owed on the same shape.** `charly kubevirt
migrate` CREATES a `VirtualMachineInstanceMigration` for a guest (`migrateVMI` in `migrate.go`), which is
precisely the state change D-VERB-1 forbids a verb to perform, and `migrate` is already the schema
reshape's word (D-SCH-5). `charly kubevirt gpu` only PRINTS the GPU host devices the entity's
VirtualMachine CR would carry (`GPUCmd.Run` → `RenderVirtualMachineGPUs`), which is a dry run of the
node's own rendering, while D-HW-9 *the solver chooses the GPU and the lease names it* gives the device
itself to the lease.

A.9 records the trade once, and both rows cite it:

| what the row claimed | what an author has instead |
|---|---|
| a live migration of a guest | READ with the `kube` verb's `resource` operation — a `VirtualMachineInstanceMigration` is a resource the API serves |
| a DataVolume import | READ the same way; the guest's disk is the `vm`'s `from:` (§14.2 puts every conversion in the source's `os`) |
| `charly kubevirt … gpu` | `charly box inspect`, a dry run of the node's own rendering |
| the GPU device itself | the `gpu:` need and its lease (D-HW-9, and A.9's host-driver-mode row) |

Two cells that were wrong are CORRECTED rather than carried: the `today` cell of the command row (it
said `gpu` "reports or sets GPU host-device readiness", but the subcommand only prints the declarations
the document already makes) and the `dulling` cell of the deploy row (the vanished "no `migrate`" claim,
which the `_method` table falsifies). No vocabulary was invented: `migrate` stays the schema reshape's
word, and neither row invents an operation the design would have to carry.
