# 2026.279.1744 — fix(harness): a pi session worktree materializes a scoped module set, not the whole graph

## Summary

A pi session worktree cost **~6 minutes and ~600 MB for every cutover**. This is the RCA, the fix, and the guidance that keeps it from regressing.

`charly_worktree_create` ran `git submodule update --init --recursive` unconditionally: all **425** submodules, each cloned into a **worktree-private** object store, none of it shared with the main checkout. Failure signatures were enumerated first — four independent mechanisms under one symptom:

| # | Signature | Mechanism | Missed control |
|---|---|---|---|
| S1 | 425 submodules cloned per worktree | an unconditional graph-wide init, whatever the cutover touches | nothing bounded the materialized set to the cutover's need |
| S2 | 376 MB worktree-**private** module objects per worktree | a linked worktree gets its OWN `modules/` git dirs; git shares only the SUPERPROJECT's objects (`commondir: ../..`) | no `--reference`, so every clone copied instead of borrowing |
| S3 | 13 worktrees + 2 branches resident long after their PRs merged (measured 2026-10-06) | `charly_worktree_remove` depends on a session remembering to call it | no reap on landing (see Follow-ups — blocked) |
| S4 | `git add … .pi/ledger/…` staged the file and exited 1, aborting the mandated `add && commit` chain | an **unanchored** `ledger/` in the clone-local `.git/info/exclude` ("mirrors plan/") shadowed the **TRACKED** `.pi/ledger/` | nothing detects a local exclude rule shadowing tracked content |

**Fix.** `charly_worktree_create` now always materializes `charly` + `marketplace` — the modules the harness's own tools and gates read — borrowing their objects from the main checkout (`--reference`), with a `modules` argument that **adds** to that set, never passes `--recursive`, and names the reap command in its own output.

The worktree still isolates the **mutable** half of a session (working tree, index, branch, its own `charly/bin/charly`), which is what lets several sessions work from the same umbrella at once. Only the **immutable** object stores are shared. That split is the whole point: share objects, never working trees.

## Measured cost model (425 submodules, `main`)

| Step | Measured |
|---|---|
| `git worktree add`, nothing materialized | **0.019 s** (0.016–0.019 s across runs) **· 3.8 MB**; metadata 5 files; superproject objects shared |
| `submodule update --init --recursive` (former) | 17.2 s for 20 modules ⇒ ~0.86 s/module ⇒ **~6 min** for 425; **376 MB** private objects + ~230 MB checkouts |
| `submodule update --init --reference …` (now) | 0.5–0.8 s/module; module stores **1 MB**; `alternates` engaged |
| the per-worktree binary | ~1m20s · 51 MB — required, never shared (R9 + concurrent sessions) |

Two hypotheses were measured and **refuted**, recorded so they are not re-proposed: the automatic `submodule.alternateLocation=superproject` does **not** engage for a linked worktree (0 `alternates` files, 16 MB vs 23 MB = noise), and `--depth 1` does resolve the recorded gitlink but buys ~3 MB on a small repo at the cost of history.
