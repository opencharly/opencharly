# 2026.288.0803 — chore(pins): record the current released tags of marketplace and pod-charly-automation

## Summary

Two gitlinks recorded at their repo's default-branch HEAD, plus the harness-config binding the
first of them requires.

| path | from | to | what it records |
|---|---|---|---|
| `marketplace` | `1ca39e58` | `0f68fdd` | the skill corpus, whose refs list projects every skill this programme corrects |
| `pod-charly-automation` | `36927502` | `6418fa8` | the `crabbox-deploy` skill's owning repo, now carrying the merged `v2026.288.0732` |

Both are forward moves — checked, not assumed: `git merge-base --is-ancestor <old> <new>` is true
for each, so neither records a rewind.

**The marketplace advance is not a pure record, and the gate is what said so.** Its default branch
has gained a **`firecracker` family** — a new microVM substrate — so advancing the gitlink without
binding that family in the umbrella's harness config would ship a corpus skill no session can load.
`charly task verify` failed on exactly that, in two halves:

```console
$ charly task verify
FAIL  [skills] paths covers every marketplace skill/agent dir (missing: marketplace/firecracker/skills)
FAIL  every marketplace/<family>/skills/<name>/SKILL.md is bound by a .dsh/skills/<name> entry (353 corpus skills, missing: firecracker:firecracker)
```

The second half only appeared after fixing the first, because a coverage failure short-circuits the
report. The fix is therefore two files:

- `reasonix.toml` — `"marketplace/firecracker/skills"` added to `paths`, in sorted position between
  `filebrowser` and `hermes`;
- `.dsh/skills/firecracker` — the committed symlink into the corpus
  (`../../marketplace/firecracker/skills/firecracker`), matching the 352 siblings, so the DSH arm
  can actually resolve it.

Deliberately **not** advanced, with the reason stated rather than left implicit:

- `distro-cachyos` is behind (`673b1b6b` -> `cd5de3f`), but Policy B binds it to `charly`'s own
  `box/cachyos` gitlink, which is `673b1b6b`. Advancing the umbrella's copy alone fails the
  `policy-b` step; the pair moves from `charly`'s side first, which is a `charly` PR and not a pin
  record.
- The four Crabbox consumer pins that decide which CLI the beds actually test are part of a held
  change: written, `charly box validate`-green, and not pushed, because the R10 bed for a runtime
  change to a `disposable: true` target cannot currently build on this host
  (`opencharly/charly#937`). This PR neither touches nor claims them.
