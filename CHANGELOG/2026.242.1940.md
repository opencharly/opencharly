## Nothing was broken before this

Worth stating, because the opposite reading invites a hand-pin. Before this sync the umbrella
pinned `charly@91d96a8d` **together with** `distro-omarchy@e2ae5576` — and that was
**consistent**, because `91d96a8d`'s own `box/omarchy` gitlink *is* `e2ae5576`. The umbrella
held an older, coherent snapshot. `verify` said so:

```
check-policy-b: OK — 6 distro pins equal charly's gitlinks
verify-pins: OK — 349 submodules, policy B holds
```

So this is a deliberate roll-forward, not a repair.

**The invariant is that a distro pin equals THE COMMIT CHARLY PINS** — not that submodule's
latest `main`. Comparing against the submodule's `main` is a different and wrong comparison,
and acting on it would mean hand-pinning the umbrella to a commit charly does not pin, which
the umbrella rulebook names as an R4 violation.

### One misleading failure in between, recorded because it will recur

The first post-sync run reported:

```
FAIL: charly: dirty working tree
```

That is not dirt and not a pin violation. Advancing the umbrella's `charly` gitlink moves
charly's *own* `box/omarchy` pointer, but the checkout inside `charly/` stays at the previous
commit, so charly's tree reads as modified:

```
$ git -C charly status --porcelain
 M box/omarchy
```

`git -C charly submodule update --init --recursive box/omarchy` resolves it, and the rerun is
the green result above. Anyone syncing a superproject gitlink will hit this; the message names
the wrong thing.
