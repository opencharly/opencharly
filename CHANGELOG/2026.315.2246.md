# 2026.315.2246 — docs: state where the four roots are resolved — the contract module, re-exported by the sdk kit

## Summary

The design record said the four roots are resolved in `sdk`. They are not, any more — and leaving
that sentence in place would make the org's own normative document false about the code three
repos just landed.

Three claims move, and nothing else:

| where | was | is |
|---|---|---|
| `DESIGN.md` D-STORE-1 | "The roots, resolved by one sdk package" | resolved by ONE resolver on the contract surface — `spec/storeroot` — with `sdk/storekit` re-exporting it as its own API; the four path clauses are UNCHANGED |
| `DESIGN.md` CI-gates | "store roots only via sdk (D-STORE-1)" | "store roots only via the contract resolver (D-STORE-1)" |
| `DESIGN.md` D-SDK-1 | "the store and its roots (§20)" among the sdk mechanisms | "the store (§20)" — the roots' home is D-STORE-1's to state |
| `TODO.md` store phase | "**The store and the roots** (`sdk/storekit`)" | names both homes: `sdk/storekit` for the store, `spec/storeroot` for the roots it lives under |

**Why the move happened, in one line each** (the three producer legs, all merged):

- opencharly/spec#303 — `spec/storeroot` now owns the four-root computation and the single
  `CHARLY_CACHE_DIR` override (tag `v0.2026315.2118`).
- opencharly/sdk#499 — `storekit/roots.go` re-exports it (`type Root = storeroot.Root`, the four
  consts, `Dir`/`CacheDir` delegating), so no plugin's import changes (tag `v0.2026315.2134`).
- opencharly/charly#1121 — core's `charlyDaemonPids` resolves its two roots through the contract
  surface, which is the only way the plugin HOST could reach the ONE resolver at all, because core
  may import only `spec/*`.

**What did NOT change in the record**: no requirement id is added, removed or renumbered; no table
gains or loses a row or a cell; §10.1's vocabulary, §12.4's rules and the parity ledger are
untouched. The change is prose inside four cells — two of them D-STORE-1's and D-SDK-1's own text.
