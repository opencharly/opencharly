# 2026.300.0018 — feat(gate): the PR body gate bounds its size, and reads its fences and sections

## Summary

Head `3141963bd1d099274e06c64068d5711ffed9820c` — the umbrella's own PR body gate learns three things it was never asked: the body's SIZE, whether its FENCES PAIR, and whether the sections the body must carry are PROSE rather than text inside a fenced block. The diff is 6 files changed, 382 insertions(+), 19 deletions(-) against `origin/main`. It discharges opencharly/opencharly#716 — the push path has no control on the body's size, so a body over the cap is refused by the API only after the push has already succeeded — and opencharly/opencharly#717 — the body gate never asserted that a body's fences balance, so one fence too few shifted every later pair, and from that point the arms read the evidence as prose and the prose as evidence.

The size cap is ONE number, in `scripts/lib/pr-body-cap`, and BOTH readers take it from there: the reconciler that judges a body against the diff it is published with, and the builder that renders the sync PR's body. A cap that cannot be read, or that is not a positive integer, fails loud in both, so a cap nobody chose can never become a second cap that disagrees with the first.

`charly task verify` now runs the pre-push body gate, so the gate's fired assertions are reachable from the repository's own gate and not only from the commit hook.

## Correction to opencharly/opencharly#718

The record opencharly/opencharly#718 published carries one sentence this change corrects and one figure this change corrects. The published entry stays standing — a record the tree falsifies is not rewritten in place — and the correction is readable beside it.

**The pathspec sentence overstated the guard's view.** The record says the parent's own uncommitted work "is still reported, and only the declared nested paths leave the view". Measured against the real `scripts/init-submodules.sh`, that is true of the parent's WHOLE view and NOT of the guard's view. A STAGED change to a declared nested path's OWN gitlink IS the parent's own uncommitted work, and the parent's whole view reports it as `M  core` — but it sits AT the excluded path, so the guard's view, which excludes that path by PATHSPEC, does not carry it. The advance then reaches git's own checkout, and git decides, measured BOTH ways: it REFUSES when the recorded gitlink's tree records a DIFFERENT commit for that nested path, and the checkout leaves that entry alone when it records the commit the current tree already records. Neither way is the staged change LOST.
