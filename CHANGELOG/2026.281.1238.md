# 2026.281.1238 — docs(design): a plugin declares its own OS packages, gated by a default-off local_install

## Summary

An OS package a plugin needs in order to run — `podman` for the pod kinds, the `qemu`/`libvirt` set for the vm kinds, the nerdctl stack, `kind`, `openssh*`, `gocryptfs`+`fuse3`, `gnupg`+`pinentry`, `rust`+a monospace font+`procps-ng` for `record: gif`, `tesseract` for the `artifact_contains_text:` assertion — is declared today in **charly's own package**: `charly/packaging/charly.yml`'s `packaging.formats.*.depends` carries **222** entries across its **6** `depends:` lists, and no plugin candy declares an OS package it needs *on the host* in order to run. DESIGN.md never said where those packages belong, and nothing said whether charly may install them on the host at all. This lands both halves as design, in `DESIGN.md` and `TODO.md` only:

- **`D-CANDY-6`** — on a plugin candy, `package:` and `os_override:` declare the OS packages the plugin needs in order to run, resolved against the `os` family of the host that runs it. The `packaging:` metadata that builds charly's own native packages declares only what core needs; a plugin's packages enter those packages through the **union of the plugins a variant lists, never as a transcribed list**, and `charly local-install` installs them only when the configuration allows it (`D-STORE-9`). Pointered from §8.1 (the plugin's config) and carried by the §11.1 candy field rows for `package` and `packaging`.
- **`D-STORE-9`** — the requested switch: `local_install` is **`false` by default**, so charly installs nothing on the host that runs it unless the operator enables it. `charly local-install` is the **one** command that installs a declared plugin's OS packages there; it refuses while the switch is `false` unless `--local-install` enables the install for that invocation, and while it is `false` every other path reports the missing packages (`charly doctor`) or fails naming them. Wired into `D-STORE-2` (the user configuration holds it, set through `charly config`), the §19 host command group, and `D-CLI-5` (a plugin's OS packages are the one requirement beyond the `charly` binary itself).
- **`TODO.md`** — the operator decision in §1 and work item **6.9**: the current-state evidence, the per-plugin config migration, and the code work (`release-package` unions a variant's plugins' packages; the new `local-install` command installs only under the switch; the transcribed lists are deleted).

**Scope, stated plainly.** This diff is `DESIGN.md` and `TODO.md`, and nothing else. No code, no pin, no submodule gitlink, no plugin candy, no behavioural config. Two surfaces are deliberately left to their owning repos, because they are the *current state* this design replaces and editing them here would be an edit across a submodule boundary: `charly/AGENTS.md` R9's rule that runtime OS dependencies belong in the charly candy's `packaging:` section, and the transcribed lists in `charly/packaging/charly.yml`. Both are the implementation side of work item 6.9, whose evidence is in that item.

`DESIGN.cue` is deliberately untouched, and that is a claim about the design's own consistency control, not an omission: the rule is not schema-expressible (`packaging:` is `#Opaque`, owned by the operations plugin, and the candy `package:`/`os_override:` fields already exist), so a `// D-CANDY-6` tag would have had no line to enforce and would have demanded a `design/negative/` case for a shape that does not exist. Control 2/5 below is the check that makes DESIGN.md and DESIGN.cue state the same design, and it passes on this head.

Closes #439.
