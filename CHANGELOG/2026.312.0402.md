### `kind:kubevirt` — the amendment it named, D-DEP-1, lands

D-DEP-1 said `pod` and `vm` are written identically, and named only two things that differ between
them: driver data and the `os` boot content. The row's complaint was that a guest cannot say where
it lands — no machine body carried a selector, while `#ClusterPodDefault` is cluster-wide. But
`#ClusterPodDefault`'s own comment already promised the workload one, "where the cluster schedules a
workload when the workload names no selector", so the missing piece was an unwritten field rather
than a decision.

`node_selector` joins `#MachineFields` beside `from`, `publish` and `config`, so a `pod` and a `vm`
name it identically (D-DEP-1). The `#MachineFields` table names it, and D-DEP-1's rule now states
it: a workload that is a guest of a cluster says where it lands, its own `node_selector`, with the
cluster's `pod_default` applying where it names none — so the placement of a `vm` written inside a
`kubernetes` body is the `vm`'s to state, not only the cluster's. The `check-kind-workload` example
gains a KubeVirt `guest`, a `vm` written inside a `kubernetes` body, which exercises the field.

Two halves of that row have no honest home, and §A.9 records them instead. A boot medium that is a
claim the cluster already holds (and a `clone` of one) is not a source: D-SRC-1 gives a source
exactly one origin, §14's concept table makes it an external starting point — one origin plus its
`os` — and a claim is the cluster's own storage, read with the `kube` verb's `resource` operation.
A raw `affinity` object is not a `pod` or `vm` body's to carry either: D-HW-5 gives that body one
open field and limits it to what the vehicle's own shape needs, while the raw scheduling payloads
stay with the cluster in `#ClusterPodDefault` as S10's open struct.

### `kind:firecracker` — the host side has an owner, and it is not the document

The row's instance side already lands on `config:`. Its host side — the VMM release pin with its
jailer posture, the containerd snapshotter with its devmapper device, the tap/CNI path with
forwarding, and the fireactions runner pool — has no home in an authored body and never will:
D-DRV-1 makes a driver a row rather than a kind, D-HW-5 bars a security option and a device path
from every body (and S10's `config:` reaches only a `pod` or `vm`), and D-STORE-2 gives what the
user sets to the user configuration, where a driver plugin's own section holds it.

So the row accepts the retirement, and §A.9 records the trade. The machine that runs a `vm` is the
operator's: its section in the user configuration, installed through `charly local-install`
(D-STORE-9) and reported by `charly doctor` (D-HW-3). A runner pool is a host service, so it is a
candy's `service:` in a `local` deployment, never a field of the machine it serves. The extra drives
and the rate limiters go with the host surface: a drive for which the design defines no capability
type is one its plugin adds (D-HW-5), never a device path in a document.

### Corrected while settling

- The kubevirt cell read the guest's `node_selector` as homeless. `#ClusterPodDefault`'s comment had
  promised it, and the word was already in the schema, so it was an unwritten field rather than a
  design decision — it lands here instead of being traded away.
- The firecracker row's `action` was `amend D-DRV-3`, and that amendment could never settle it.
  D-DRV-3 declares what a driver row GIVES; a driver's host surface is not a thing a row authors —
  D-DRV-2 keeps the driver out of the document, D-HW-5 bars the settings, and D-STORE-2 is where
  they live. The action becomes `accept retirement`, with §A.9 holding the trade.

Both cited schema ranges were re-read against the tree rather than trusted: `spec/schema/firecracker.cue:35-61`
is exactly the `#Firecracker` body, and `spec/schema/kubevirt.cue:18-77` is exactly the `#KubeVirt`
body.
