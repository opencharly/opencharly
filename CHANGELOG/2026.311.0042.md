# 2026.311.0042 — feat(design): a cluster names its kubeconfig file and its KubeVirt platform (batch 54)

## Summary

Batch 54 of the DESIGN amendments (tracked in #838). Round 93's review named the two gaps that kept
`kind:kubernetes` dulled after batch 48 closed nine of its fields: **the kubeconfig FILE path**, and **the
KubeVirt platform knobs**. Both are read from the product's own `spec/schema/kubernetes.cue` rather than
guessed:

```cue
kubeconfig?: string              // the FILE the cluster is reached through
kubevirt?:   #KubernetesKubeVirt // enabled, cdi_enabled, cdi_namespace, use_emulation,
                                 // default_storage_class, default_instancetype,
                                 // default_preference, snapshot_class, virtctl_version
```

`#KubernetesFields` gains `kubeconfig` — a **file path**, distinct from `kubeconfig_context`, which selects a
context *inside* it — and `kubevirt` (`#ClusterKubeVirt`), the platform a `kind:kubevirt` target resolves its
cluster side from.

**`kind:kubernetes` becomes sharp**: every field its capability text names now has a home.

Two vocabulary collisions, both real: `snapshot` is a §2 **Not** term, so the policy is `volume_snapshot`;
`substrate` is banned too, so the field speaks of a `kind:kubevirt` **target**.
