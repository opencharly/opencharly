# 2026.299.1112 — fix(init): materialize a materialized path's nested level (#647)

Closes #647

## Summary

Head `e4a6f6d9e476a1909f0db502b2838c690ed8aee5` — the commit this PR pushes: **1 file changed, 284 insertions(+), 5 deletions(-)**.

`scripts/init-submodules.sh` materialized a requested path but not the path's **own**
submodules, so a path that was already at its recorded gitlink kept an **absent nested
level**. The umbrella's currency report then cannot JUDGE an edge whose source is a nested
pin: the edge arm asks for the twin's checkout, and without one it prints
`differs (no checkout of box/cachyos to judge ancestry)` — a state that names nothing —
instead of an ancestry verdict that names the producer.

The mechanism is git's `--recursive`, and **where it sits**. It brings a path's nested
submodules in only when the very call that materializes the path is the one that recurses.
A path that was materialized EARLIER is already at its recorded gitlink, so `advance_path`
returns before git is called at all — and the nested level stays absent. The post-condition
is therefore the **deep** one #647 names: every requested path's own declared submodules are
materialized **at the gitlinks that path's CURRENT tree records**, because a twin that is
present but a revision behind the parent's record is still a stale twin. That post-condition
holds for every twin that can be brought to its record; the one shape where it cannot — a
twin that carries work — is reported and left alone, and the run fails rather than
discarding it (see *Rulebook compliance*, and #711).

The nested level is materialized by **the same script, re-rooted at the path's own root** —
one implementation of the path lifecycle, applied at every level (R2), under the same policy
(R6): a twin behind its record is advanced, a twin already at its record is left where it
is, and a twin that carries work cannot be brought to its record without discarding that
work — so it is REPORTED by name and left alone, and the run exits NON-ZERO. The pass runs
only for a path sitting AT its recorded gitlink, because the nested gitlinks live in the
path's own tree.

`advance_path` no longer carries `--recursive`, and the reason is **measured, not
stylistic**: git's recursion force-checks a nested submodule out to the recorded gitlink and
**silently discards its local commits** (rc=0, no warning, the nested checkout's own commit
dropped from its HEAD). A fix that simply ran the recursive command for every path would
therefore introduce exactly the R6 clobber the script's own `land_pin` guard exists to
prevent. `--recursive` stays on `materialize_uninitialized` — the one call that touches a
path with no subtree at all, where nothing under it can be clobbered.

The advance's "has UNCOMMITTED changes" notice now names **both** causes — the path's own
uncommitted work, or a nested path that does not match the gitlink it records for it —
because git reports the nested cause in the same porcelain view, and a path whose own tree
is clean does NOT have uncommitted changes. The old text was false for that state, and this
change makes that state reachable: it materializes the nested level, so a nested divergence
now reaches the parent's view. The original notice named no nested path either — it said
only "has UNCOMMITTED changes" — so this is a WIDENING of the text, not a loss of a name;
the specific twin is named by the nested pass, at the nested level. The sequencing question
behind it — should a descendant's state hold the parent back at all — is filed, not decided
here (**opencharly/opencharly#711**).

The scope is `scripts/init-submodules.sh` alone — the script and its own `--self-test` live
in that one file. Not the pin contract, not how currency is reported, not a new gate, and
not `charly task init --all` by default — the working set stays light.
