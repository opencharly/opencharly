# 2026.243.0941 — fix(sync): fetch a charly-pinned commit before switching to it

## Summary

The gitlink sync ran green for two dispatches and then died at `Bump pins`:

```
== charly-pinned repos (exactly charly's gitlinks) ==
fatal: unable to read tree (677dbbe038f2daba286dee1d00112a38547bfc6f)
##[error]Process completed with exit code 128
```

One line changed in `scripts/sync-gitlinks.sh`: fetch a pinned commit before switching to it.

## Root cause

**The message names a TREE and the problem is a missing COMMIT**, which sends you at the wrong
object. I went after charly's own checkout first, before noticing that `677dbbe0` is not something
charly *contains* — it is what charly's `box/cachyos` gitlink **points at**, i.e. a
`distro-cachyos` commit.

From there it is straightforward. A `distro-*` ref under policy B is an arbitrary commit — whatever
charly records — not a branch tip. CI's submodule clones are **shallow** (`actions/checkout` fetches
them at depth 1), and `git fetch origin` brings only tips, so that commit is simply not present and
`switch` cannot resolve it.

It worked for two dispatches purely because charly's gitlinks happened to point at commits the
shallow fetch already had. The moment charly adopted a newer `distro-cachyos` snapshot — `charly#507`,
earlier today — it stopped.

## How tested

**Reproduced outside CI, byte-identical**, by doing exactly what `pin()` does to a shallow clone:

```
$ git clone --depth 1 …/distro-cachyos dc
$ git -C dc fetch --quiet origin
$ git -C dc switch --detach 677dbbe038f2daba286dee1d00112a38547bfc6f
fatal: unable to read tree (677dbbe038f2daba286dee1d00112a38547bfc6f)
```

**The fix verified as an A/B on that same shallow clone:**

```
--- OLD (fetch tips, then switch)
fatal: unable to read tree (677dbbe038f2daba286dee1d00112a38547bfc6f)
old_result_head=7b4e85f                     ← still on the wrong commit

--- NEW (the fix)
  commit absent after tip fetch -> fetching the SHA explicitly
  switch OK -> 677dbbe
```

**A first hypothesis, disproven and recorded so it is not re-chased.** I suspected the failing read
was charly's own `ls-tree HEAD box/cachyos` against a shallow checkout. It is not — that works:

```
$ git clone --depth 1 …/charly && git -C charly fetch origin && git -C charly switch --detach origin/main
$ git -C charly ls-tree HEAD box/cachyos
160000 commit 677dbbe038f2daba286dee1d00112a38547bfc6f	box/cachyos      ← exit 0
```

That is what identified `677dbbe0` as a *distro-cachyos* commit rather than a charly object.

**The workflow itself, dispatched from this branch:**

```
run 33377411789  (ref: fix/sync-fetch-pinned-commit)   completed/success
  → opened opencharly#85, 34 gitlinks
```

The previous two dispatches died at `Bump pins`; this one **got past the
`== charly-pinned repos ==` loop** — the exact loop that was failing — and completed. That is the
proof, and it is the only thing that could be: the failure only reproduces when charly's gitlink
points at a commit the shallow submodule fetch did not bring.

`#85` itself is closed rather than merged, for the usual reason: `workflow_dispatch` cuts the sync
branch from whatever ref it runs on, so a branch-dispatched run bundles this `scripts/` change in
with the gitlink bumps and the body's "gitlink-only" classification is then untrue. A scheduled run,
or a dispatch on `main` after this lands, carries only gitlinks.

## Why the guard is `cat-file -e`

The common case is a branch ref (`origin/<default>`), already fetched by the line above, so the
guard short-circuits and costs nothing. It also means a server that refuses SHA fetches still takes
the plain path rather than hard-failing on the extra fetch.

## The failure mode was safe, which is worth recording

`set -euo pipefail` turned the failed `switch` into a hard exit, so the run died rather than
`git add`-ing a submodule still parked on its old commit. Without it this bug would have produced a
plausible-looking sync PR carrying one silently stale pin — far worse than a red run. The A/B above
shows exactly that latent state (`old_result_head=7b4e85f`).
