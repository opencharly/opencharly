# 2026.327.0848 — feat(design)!: separate need: from nesting, define the OCI label contract, and gate GRIEVANCES.md

## Summary

Closes #1233.

The examples in GRIEVANCES.md claimed to be "written in the grammar DESIGN.md defines", but nothing checked that claim. One example in particular, `need: nesting: {container: {}}`, mixed two ideas: a **need** (what a node must be *given* in order to run) and **nesting** (*where* a deployment runs), which D-NEST-1 already says is expressed by tree position alone. This PR fixes that in DESIGN first, rewrites GRIEVANCES against the amended target design, and makes the design check hold GRIEVANCES to it.

### DESIGN amendment (DESIGN.md + DESIGN.cue, together)

- **A need is never a place (D-CAP-7, new).** The `nesting` capability type is removed: `_nesting`, `_nestingWord`, its `_capability` row, its §8.1 row and its three §9.1 grant rows. §8 gains a paragraph stating the difference between the two ideas.
- **The grant follows tree position (D-NEST-7, new).** The deployment-kind row gains `host`: what an inner node of that kind needs from the deployment it is written in. Today that is `_#EngineHost` for `pod` and `kubernetes`, and `_#HypervisorHost` for `vm`. A node written inside a `pod` or `vm` adds that `host` to its parent's needs, derived and never authored. The parent's kind grants it like any other host need: on a `vm` parent, `kvm` comes through the nested-virtualization CPU mode (§9.1 `device` row). §17.2 gets the derived-need table, and D-CAP-6 now counts these derived needs. §17.4 gets a `nested-deployment` example: a pod, a VM inside it, and a pod inside that VM.
- **`userns` moves to `isolation`.** `isolation: {userns: {}}` is a boundary need, next to `microvm` (D-HW-6, D-HW-7 and the `boundary-need` example are updated).
- **Rootless by default (D-HW-10, new).** A deployment is rootless unless a need in its stack is `privilege: rootful`. §9 says this in its opening paragraph.
- **The OCI label contract (§16.6, D-CANDY-8 and D-CANDY-9, new).**
  - `#Labels` has one word per concern — `box`, `release`, `os`, `service`, `need`, `use`, `provide` and `step` — each the label `ai.opencharly.<word>`.
  - Each value is the JSON encoding of that concern's authoring definition, so the label contract adds no shape of its own (D-SCH-1).
  - A label carries checks only (`#LabelStep`), with every phase written out.
  - D-CANDY-4 is reworded to match ("resolved checks").
- **Appendix A no longer names the retired `TODO.md`.** #1193 removed it from every gate, but A.1, A.4 and A.11 still said the controls read it. "TODO.md 2.16" now points at the open census issue #945.
- **New examples and negatives.** Two new examples: `labels` (a new A.5 mode, validated by `cue vet -d '#Labels'`) and `nested-deployment`. Four new negatives: `need-nesting` (D-CAP-7), `authored-nest-host` (D-NEST-7), `label-unknown-key` (D-CANDY-8) and `label-install-step` (D-CANDY-9). The ledger rows of `design/parity.tsv` and `design/dulling.tsv` that named `nesting:` now name the tree-position form.

### GRIEVANCES.md

- **Block YAML in every example.** The only `{}` left is an empty leaf entry, because YAML has no other way to write an empty mapping (the schema requires a struct there).
- **Plain status quo.** Each "The status quo" is now prose that any reader with DevOps experience can follow without knowing this project's vocabulary.
- **§4 states rootless as the default.** The `need: nesting` example is replaced by candyboxing written as a tree — a VM inside a rootless pod, and a pod inside that VM — and the prose names exactly what each position derives.
- **§5 shows the decoded labels** that the `hello-web` box carries.
- **Every example is marked** with `<!-- example: … -->`.
