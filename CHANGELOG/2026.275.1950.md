## Finding 3 — the pasted `task verify` line described a state that cannot exist; here is the real one

The verdict was right that a `FAIL: sdk: HEAD … != gitlink d52f17c6…` line cannot describe a real submodule state. It is a **git directory walk-up artifact**, and this is the measurement, taken on this head (`36a648e`):

```
$ ls -a <worktree>/sdk            # sdk/ is EMPTY in a worktree
.  ..
$ git -C <worktree>/sdk rev-parse HEAD              → 36a648ee3c8fd49cdf255bbeb2e77d99d4f17d70
$ git -C <worktree>/sdk rev-parse --show-toplevel   → <worktree root>
$ git -C <worktree> rev-parse HEAD                  → 36a648ee3c8fd49cdf255bbeb2e77d99d4f17d70   ← identical
$ git -C <worktree> ls-tree HEAD sdk                → 160000 commit d52f17c64c2056e6c64c295d38633f17d60084a8
```

`sdk/` is an empty directory, so `git -C sdk` resolves the **superproject** — its `HEAD` is this branch's own commit, which is exactly the absurdity the verdict spotted (the sha it flagged, `807abd4`, was this branch's head when that run was taken). The step never checks that a submodule is *initialized* (`[ -d "$path" ]` is true for an empty directory), so it reports the walk-up as a HEAD mismatch. That is a defect in the step, now filed as **opencharly/opencharly#337** with this measurement and the step's own lines.
