## The wrong fix, and why the second commit exists

The first commit here ran `verify-pins.sh` in the job. The run rejected it:

```
FAIL: charly nested submodules not at their gitlinks
```

Not a pin problem. The check is `git -C charly submodule status --recursive | grep -E '^[+-]'`,
where **`-` means UNINITIALISED**, and this job uses `submodules: true` — non-recursive. charly's
nested submodules never exist here, so it can only fail; and initialising them would check each out
**at** its gitlink, making it pass **by construction** and assert nothing.

That gate is meaningful for a human's local tree, where nested state can genuinely have drifted. On
a fresh clone it is vacuous either way — so running it would have swapped "a promise" for "a
meaningless gate result", which is the same defect A1 blocked wearing a different hat.

Both commits are kept. The branch was already pushed and force-push is forbidden, so the wrong turn
stays in history with the correction on top — which is the honest record regardless.
