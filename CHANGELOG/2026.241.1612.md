# 2026.241.1612 — docs: the candy cutover plan says what is actually true now

## Summary of changes

`plan/candy_to_repo.md` is a **living reference** — it is what someone consults to learn how the
candy cutover works — and three of its statements are now false. Two of them would send a reader
down a path that fails.

### 1. The status header

Read *"In progress (Phase 2 — plugin candies). Last updated 2026-08-25."* `charly/candy/` is empty
and the directory is gone (`opencharly/charly#457`).

### 2. "The `charly` meta-candy stays in the main repo"

It does not. It is **`layer-charly`**: nothing in charly referenced it by name, the distro boxes pin
`layer-charly`, and what charly kept is its own native-package metadata — packaging **data**, not a
deployable candy — now at `packaging/charly.yml`, still published as the `charly-candy-charly.yml`
release asset the six per-distro package repos consume.

The same bullet's `generate-packages` claim is **expanded rather than deleted**: charly keeps a thin
re-export **shim** at `tools/generate-packages/`, *not* under `candy/`, because that is what makes
`charly generate-packages` resolvable from a checkout. The doc now records **why it cannot just be
deleted** — a remote candy ref does not register a command word (measured: a project pinning only
the plugin exits 80), and making it do so would put a network fetch in CLI startup.

### 3. "Initial commit lands directly on `main` + a CalVer tag" — the one that actively misleads

Pushing `main` is blocked by the pre-push gate. And a fresh repo needs three settings **before its
first PR**, each failing differently:

| Missing | Symptom |
|---|---|
| `allow_auto_merge` | the validator PASSes, then its final step dies on GraphQL `Pull request is in unstable status` |
| the three dispatchers on `main` **before** the first PR | the PR merges, **no tag appears**, and `tag-on-merge` shows no runs at all |
| the org `main branch protection` ruleset | no required check |

The dispatcher one is the subtle one: `tag-on-merge` fires on `workflow_run` of the validator, and
`workflow_run` only fires for workflows **already on the default branch** — so the PR that
*installs* the dispatcher can never be tagged by it. That matters because the marketplace refs list
pins repos **by tag**, so an untagged repo cannot be referenced.

All three were learned by hitting them across the **14 repos created in this phase**; 13 needed a
tag backfill. The recipe is written down so the next repo does not.

### On the attribution footer

The previous review asked for the parenthetical to be "a confidence, not the attribution tier".
In this rulebook they are the same thing. `AGENTS.md`'s table is headed

```
| Confidence | Required proof |
```

and its rows are exactly `fully tested and validated`, `analysed on a live system`,
`documentation reviewed`, `syntax check only`, `theoretical suggestion`. The rulebook's own
example footer is

```
*Assisted-by: pi openrouter/deepseek/deepseek-v4-flash (fully tested and validated)*
```

— a tier name in the parenthetical. A percentage would not match any documented value.

This exact form was accepted on every PR merged in this series, including `opencharly/charly#457`,
`opencharly/marketplace#243`, `opencharly/plugin-marketplace#8`, `distro-arch#31` and
`distro-fedora#44`. The footer is left in the required form; if a different literal is wanted,
naming it will get it changed immediately.
