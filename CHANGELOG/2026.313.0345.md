# 2026.313.0345 — feat(check): a pin must be at a tag or one step above one

## Summary

Every release lands as a squash merge, `tag-on-merge` writes a `CHANGELOG/<CalVer>.md` commit on top of it, and this umbrella's pin advances to the branch tip — so the tip is one CHANGELOG commit above the tag, and `git ls-remote --tags | grep -F <pin>` is empty for it. Nothing related a pin to a tag: a pin left untagged for a different reason read exactly like a healthy one, and `tag-on-merge` could fail after the merge with no detector — it did on 2026-11-09 (`HttpError: other side closed`, run 42553401961), filed as opencharly/.github#286. The record of the gap, with its measured instances, is opencharly/opencharly#793.

`scripts/design-pintag.sh` is a sixth control of `bash scripts/design-check.sh`. It reads every pin from the tree's index (`git ls-files --stage`), and each module from `<git-common-dir>/modules/<path>` at the pinned commit — never from a checkout — and answers one question per pin: at a tag, one CHANGELOG commit above one, a chain of CHANGELOG commits above one, the commit that installs the tag-on-merge caller, a repository with no caller, or untagged. The first five pass by rule and are reported; the last fails unless `design/pintag-baseline.tsv` records it with its reason.

**A sixth control, not a wider schema-pattern gate.** A.11 reads the CUE text of the pinned plugin modules and answers a question about the schema's shape; this reads the pin itself and answers a question about its relation to a tag. They read the same index and share nothing else, and A.2's "each control lives in exactly one script" puts the second question in a second script. DESIGN.md A.12 documents it in the shape of A.3–A.11, and A.1/A.2 now name it.

**What the offline reading can and cannot see.** A positive is a local tag ref at the pin, or at the first-parent ancestor the walk reaches — proof, and tags are immutable, so a store's tag cannot go stale into a false pass. An absence needs the remote: a tag upstream that was never fetched into the module store is invisible, and a pin fetched before its tag reads as untagged. That direction is fail-closed — it can only over-report, never bless — and every run prints the store boundary it used. `--remote` is the opt-in cross-check: for every pin the local reading called untagged it asks `git ls-remote --tags`, and it fails loud, naming the module and the URL, when a remote is unreachable. It is not the gate, because the positive side needs no network and a full sweep is one network call per ambiguous pin. Stated precisely, it cannot see: a tag never fetched (that is what `--remote` resolves), a tag deleted or moved upstream, whether a pin trails its remote's tip (the currency question, which this control does not answer), and the tag-to-merge relation beyond the first-parent line.

**The split on this tree (2026-11-09).** 409 pins in the index, all 409 judged, 0 skipped: 392 `changelog-tip`, 5 `tagged`, 2 `changelog-chain`, 3 `pre-release-process`, 5 `not-applicable`, 2 `untagged` recorded in the census. The two untagged pins are `pi-asciinema` and `layer-android-apidemos`; each is the branch tip, untagged, with no CHANGELOG commit while tag-on-merge is present at the pin and at its parent — the live instances of #286 the control now finds, recorded with their mechanism and tracked by #793.
