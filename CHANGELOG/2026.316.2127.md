**This is the first emission in this repo's record to ADD rows, and the reason is the
relocation, not a new violation.** A census row is keyed by `(file, rule, symbol)`, and its
acceptance rule is per file and one-sided: a construct occurring MORE often than its count is a
new violation, and one occurring LESS often overstates the debt. A definition that MOVES between
files therefore cannot be recorded in place — it is a removal in the old file and an addition in
the new one, by construction. Every earlier emission in this record read `added=0` for one of
two reasons: it lowered rows whose violations were fixed, or it blessed a construct that was
genuinely new (a real new row, whose rule count then ROSE). This wave is the first relocation,
so it is the first emission whose `added` count is non-zero while every per-rule count and the
total are unchanged. It is a new census category, and the next relocation — the remaining units
of `spec#304` — will hit it.

The check that matters is therefore NOT `added == 0`. It is that no rule's count increased and
the total held; both do, and the census's own control says so on the committed tree:

### `#Pipeline*` no longer exists in `spec` — what a consumer breaks on

This is a breaking change for any consumer that pins these repositories independently, and the
answer is not "none". `spec`'s pipeline module now declares one definition, and none of the
twelve the body used:

The plugin's `kind` capability has declared `InputDef: "#PipelineValue"` both before and after
this wave — and at the OLD plugin pin that def was not in the plugin's module at all, it came
from `spec` inside the composed unit:

```

```

So a consumer that composes an OLDER `plugin-pipeline` with THIS `spec` gets a composed schema
unit in which the def the provider's own `kind` capability declares resolves nowhere: the
`kind: pipeline` body gate has no definition to judge with. Whether that surfaces as a load
refusal or as a kind whose bodies go unjudged depends on the host, and either way it is a
validation hole — `charly#1126` moves `charly`'s corpus sweep onto the resolver the gate
already uses (`charly#1122`, in the pin before this one), and that resolver reads the
provider's declared `InputDef` out of the composed unit: it cannot resolve a def no module
in the unit holds. The
consumer fix is one line and is the same in both cases: pin `plugin-pipeline` at `b32a25e` or
later (the tag `v2026.316.1819`), or keep `spec` below `93011816`. The two move together.

Go consumers break loudly rather than silently: `spec.Pipeline` and its step/trigger/flow types
left `spec`'s generated Go (they are the plugin's generated `params` now), and
`sdk/workflowkit`'s graph/lower/validate symbols are gone (`sdk#502`, listed above). **Rollback:**
`git revert` this one commit. The four producers are merged and tagged, so the revert moves four
pointers and three design records back together — no data, no migration, and no history is
rewritten.
