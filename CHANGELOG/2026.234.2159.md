# 2026.234.2159 — ci: tag-on-merge on pr-validator completion (corrected RCA — auto-merge commits are run-suppressed)

## Summary

Corrects the tag-on-merge trigger design. PR #8's push-only trigger was based on a false premise; this PR replaces it with the one event whose delivery is proven in this repo — `workflow_run` on the pr-validator run that arms the auto-merge — plus `push` as a secondary path for human/bot pushes. No cron.

**RCA — why the merge itself cannot be the trigger (measured):**

The merge-into-main cannot be a GitHub Actions trigger for auto-merged PRs. Native-auto-merge squash merges (actor `app/github-actions`) **do** fire their webhook events — visible in the public event stream:

```
$ gh api repos/opencharly/opencharly/events -q '.[] | select(.type=="PushEvent") | ...'
2026-08-22T21:35:01Z sha=e222762 by=github-actions[bot]   <- PR #8 merge push
2026-08-22T21:08:34Z sha=f5d8a3c by=github-actions[bot]   <- PR #7 merge push
2026-08-22T17:36:32Z sha=fc6c603 by=github-actions[bot]   <- PR #6 merge push
```

…but GitHub Actions creates **zero workflow runs** for them (platform-level run suppression for auto-merge commits):

```
$ gh api repos/opencharly/opencharly/actions/runs -q '.workflow_runs[] | select(.head_sha=="e222762")'
(empty — no push run, no closed run, no run of any kind for the merge commit)
```

This is the same mechanism that made `pull_request: closed` never fire (0 `pull_request`-event runs in the workflow's entire history across 7 merges) and is why PR #8's `on: push` trigger produced nothing for PR #8's own merge. Human merges (PRs #1–#2) and bot contents-API commits (the changelog commits) **do** create runs — hence `push` is retained as a secondary trigger for those paths.

The cron was also unreliable: measured 21–44 min gaps vs the configured 15, PR #3's tag 4+ h late. **This design has no cron.**

**The working design:** the pr-validator run is the last actor before the merge (its final step arms native auto-merge). Firing `workflow_run` on its completion and waiting (bounded 5 min readiness probe) for the squash to land makes the **merge the effective gate** for tagging. The org's reusable sweep is idempotent and scans 24 h of merged PRs, so any timeout self-heals on the next validator completion. The rulebook's add-only backfill remains the documented failure path.
