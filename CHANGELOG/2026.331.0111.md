# 2026.331.0111 — fix(pi): worktree creation fails closed on a module clone and on a missing binary

## Summary

`charly_worktree_create` reported success for a worktree it had not built — **three times in one
session**. It is the tool AGENTS.md rule 2 mandates for starting a cutover, so this is the first thing
a session runs and the last thing it suspects.

Head `cbf6ff656896fb3a8a370e22ec83b3b1aaf4a4be` — 2 files, +126 −5.

```
Worktree created at <umbrella>/.worktrees/pi-watch-honest-state on branch feat/pi-watch-honest-state.
- Binary built at <umbrella>/.worktrees/pi-watch-honest-state/charly/bin/charly
- Modules materialized: charly, marketplace (2/2 borrowing the main checkout's objects)
```

and, the same second:

```
$ cd .worktrees/pi-watch-honest-state && ls charly | wc -l ; ls marketplace | wc -l
0
0
$ ls .worktrees/pi-watch-honest-state/charly/bin/charly
ls: cannot access '.worktrees/pi-watch-honest-state/charly/bin/charly': No such file or directory
```

**The mechanism, at path:line.** Step 3 (module materialization) and step 4 (binary build) called
`pi.exec` and **discarded the result**:

```
479:  await pi.exec("git", args, { cwd: worktreePath });
532:  await pi.exec("bash", ["charly/scripts/bootstrap-charly.sh"], { cwd: worktreePath });
543:  `- Binary built at ${worktreePath}/charly/bin/charly\n` +      // unconditional
```

A failed clone therefore fell through as an **empty** directory; the nested step (3b) then skipped it,
because an empty module has no `.gitmodules`; the build could not run at all; and the report named a
binary path regardless. The tool's own comment states the contract it was breaking — *"`pi.exec`
RESOLVES on a non-zero exit … `code` is the only failure signal there is"* (the #410 lesson, applied at
step 3b and in `charly_worktree_remove`); steps 3 and 4 predate it.

**The fix** reads both exit codes and fails closed naming the step and its stderr. For the build it goes
one step further, because an exit code is not the only lie available: a build that exits 0 without
producing the binary is refused too, and `Binary built at` prints only after the FILE is proven present,
naming the same path the check used.

A third guard — "the clone exited 0 but landed an EMPTY checkout" — was written in round 1 and then
DELETED: a clone that exits 0 always leaves a `.git`, so `!existsSync(.git)` cannot hold while the exit
code is 0. It was an unreachable arm, which CONC(a) blocks; the exit code is the signal (measured: exit
128, `fatal: repository … does not exist`).

### Spike

**RCA claim:** steps 3 and 4 discard the exit code `pi.exec` resolves, so a failed clone and a failed
build are both unreportable and the success text is unconditional.

Each candidate's SIGNAL was run, not read. A dead remote is the exact input a failed submodule clone
produces:

```
$ git clone /tmp/definitely-absent charly2 >/tmp/o1 2>&1; echo "exit=$?"; tail -1 /tmp/o1
exit=128
fatal: repository '/tmp/definitely-absent' does not exist

$ test -f charly2/bin/charly; echo "exit=$?"
exit=1

$ git ls-remote /tmp/definitely-absent >/tmp/o3 2>&1; echo "exit=$?"; tail -1 /tmp/o3
exit=128
and the repository exists.
```

- **C1 — read the exit code and fail closed naming the step and stderr. WORKS (winner).** Exit 128 above
  is the signal, and it carries git's own reason. It is also the mechanism this same file already uses at
  step 3b and in `charly_worktree_remove`.
- **C2 — assert the artifact instead of the exit code.** `exit=1` proves the signal exists, but not that
  it is sufficient: it says "something is missing" and cannot distinguish a failed clone from a failed
  build, and it names no command and no reason. **Kept as a POST-condition only** — the report line names
  a FILE, so a file is what should decide the claim — and rejected as the sole detector.
- **C3 — pre-flight `git ls-remote` each module URL.** `exit=128` too, but it is a SECOND network call on
  the happy path that still races the clone it is predicting. **Rejected:** the exit code of the real
  clone is the authority, and paying twice to guess it is not a fix.

**The spike-equivalent for the final code** (the exemption R12 names: a regression test that fails on the
unmodified tree and passes with the fix). Each guard is mutated back to the discarded-exit-code shape and
must turn the gate RED; the unmutated tree must stay green:

```
$ node scripts/check-pi-gates.mjs --self-test 2>&1 | grep -E "build's exit code|produces no binary|module clone's failure|unmutated"
  PASS  mutation 'the build's exit code is discarded' is caught (gate red)
  PASS  mutation 'a build that produces no binary is reported as built' is caught (gate red)
  PASS  mutation 'the module clone's failure is not read' is caught (gate red)
  PASS  the unmutated copy is GREEN
```

**Winner: C1 + C2's post-condition**, which is what the diff implements.
