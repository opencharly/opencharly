**The prose is the point of this change.** The umbrella's own guidance said the
**opposite** of what the product has done since plugin-task#41 landed: that *"a pin
wave needs the full set"*, because the old bump failed loud on a path it could not
advance. The new bump advances a path **with no checkout** in the INDEX — a leaf to
the tip its remote serves for its `branch=`, an edge to the twin the source's tree
records — and a path **with** a checkout is still rolled in that checkout, so the two
keep agreeing. The four surfaces that carry the wave order now say so, and they say
the order: **sync → init → verify**. The sync writes the pins, the init materializes
the checkouts *at* those pins, the verify judges them.

**The load precondition travels with it.** On a tree that was **never materialized**,
the materialization comes FIRST: the umbrella's project load resolves its manifest's
`import:` paths from the working tree, so a path with no checkout has no `charly.yml`
to read, and the wave's own first verb would not run. That fact already had one
canonical home — `AGENTS.md` Part II #2 and the README's *Start developing* — and the
surfaces that carry the wave order now point at it instead of restating it (R2).

# R1 — RCA of the wave's first failure on the light tree

**Anomaly.** The first run of the wave on the light tree failed with rc=1, and it failed
BEFORE the bump:

```
charly: error: command "task": load project: .../.worktrees/light-init/opencharly/charly.yml:
import openclaw ("./layer-openclaw"): submodule "layer-openclaw" is not initialized:
.../layer-openclaw is empty, so .../layer-openclaw/charly.yml cannot be read;
run: git submodule update --init layer-openclaw
```

**Mechanism.** The umbrella's project load resolves the manifest's `import:` entries by
LOCAL PATH, and it reads each imported path's own `charly.yml` from the working tree
(`charly.yml:6-31` declares four such paths: `charly`, `layer-openclaw`, `layer-strata`,
`plugin-strata`). A path with no checkout has no `charly.yml` to read, so the LOAD fails —
before any verb runs, and before any pin is touched. The tree had been made light by
deinitializing every path except `charly` and `marketplace`, and the deinit took the
manifest's own import set with it.

**Missed control.** The wave-order statement under test — "a wave's order is
sync → init → verify" — was written and reviewed WITHOUT the load precondition, and the
tree in which it was to be proven was prepared WITHOUT the manifest's import set. Nothing
in the shipped prose said the project must load before the first step, so the sequence as
stated is not executable on a light tree: its own first verb cannot run there. The review
that should have caught it compared the prose against the PIN contract, not against the
manifest's `import:` block.

**Blast radius.** Every umbrella verb, not only the wave: `sync`, `init`, `verify`, every
bed and every gate — all of them load the project first, so a tree without the import set
runs no task at all. The `init` verb is inside the blast radius in a way that matters: the
verb that materializes the working set cannot itself bootstrap the import set.

**Root fix (in this change).** The precondition is already stated ONCE, canonically, in
`AGENTS.md` Part II #2 ("the project cannot load before its `import:` paths exist") and in
`README.md`'s *Start developing* (the materialization precedes the bootstrap, because the
working set includes `charly` itself). What was missing is that the surfaces that carry
the WAVE ORDER — the ones this change rewrites — did not carry the precondition with
them, so the order read "sync → init → verify" on a tree where its first verb cannot
run. The fix is therefore a cross-reference, not a second statement of the rule (R2):
- `AGENTS.md` Part II #3 — the wave's order now names the materialization as the step
  that comes FIRST on a tree that was never materialized, and points at Part II #2.
- `README.md`'s *Catching up with upstream* — the same clause, pointing at *Start
  developing*.
- `charly.yml`'s `init` task header — the same fact where the materialization is defined:
  this task is NOT the first step on a fresh clone, because the project cannot load
  before its `import:` paths exist, so the binary that would run it does not exist yet.

The mechanism itself is the product's, not a defect to fix here: a manifest import is a
working-tree path, so a checkout is what it reads. The umbrella's own script is the
sanctioned materializer and is runnable WITHOUT the project (it needs only git + python3),
which is exactly why it — and not the `init` verb — is the first step of a light tree.

**Not a workaround.** `bash scripts/init-submodules.sh` is the umbrella's own sanctioned
materialization path (AGENTS.md *Umbrella-native mechanics*: "`charly task` verbs, `bash
scripts/*`"), it derives the working set from the committed sources, and it is the same
script the `init` task runs. Nothing was hand-cloned, hand-pinned or hand-checked-out.
