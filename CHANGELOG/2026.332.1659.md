# 2026.332.1659 — fix(harness): read the pre-push body gate's arm counts from prose, not from a pasted log

## Summary

Fixes the pre-push body gate's arm-count reader, which treated a verbatim, fenced gate log as the body's own prose claim.

This branch was opened for the Jupyter-retirement catch-up wave (`opencharly/opencharly#1355`, W7). That wave landed on `main` in `opencharly/opencharly#1362` — merge `b2435872893da2d648aec956590b2166835c1c0e`, tag `v2026.332.1531` — so after `gh pr update-branch` this PR's diff against `main` is exactly ONE file: `scripts/check-body-removed-identifiers.mjs`. The wave's own first push is what exposed the defect this PR fixes:

```
$ git push -u origin feat/jupyter-wave-w7
pre-push: BLOCKED — the PR body makes a claim the tree does not support.
FAIL  the body states 1 arms, and the script declares 15 — a count that contradicts its own source.
```

That line was the gate reading `charly task verify`'s own output — "every one of its seven arms has a mutation" — as the body claiming "1 arms". This PR adds the arm that block's count did not yet include.

What changes:

- **The count arm reads the body's own counts from PROSE, with fenced blocks blanked.** The pasted N/M still reads the fences, because that paste is the evidence the claim is judged against. The inline blanking chain is one `blankInline()` helper; `blankFences()` is applied only to the prose reader.
- **A new self-test arm proves both directions:** a pasted gate log is evidence, an unquoted prose count is still a claim.

The wave whose evidence exposed this is on `main` and needs nothing further here: on this merged head the census is 319, `.pi/settings.json` names `v2026.332.1434`, the `marketplace` gitlink is `7dd58e87e60df16d02cde6cc1e3a3d8afc86e41e`, and `charly-jupyter` is absent from `.claude` and `.dsh`.
