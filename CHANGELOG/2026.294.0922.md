# 2026.294.0922 — docs(containerd): correct the rootless-CDI truth, the CRIU capability and pre-flight, and the krun checkpoint boundary

Refs #551

## Summary

Eight spec divergences in the containerd/k3s/libkrun documents, found by a live RDD round on real daemons and re-measured with discriminating controls. Every claim below was measured; none is inferred. The head commit is `ef9f5f1`.

**`CONTAINERD.md`**

- **§14.2 — the rootless-NVIDIA prohibition was FALSE, and removing it changes a promise.** The old text said rootless has no NVIDIA access and told the operator to use the rootful daemon. Both symptom strings in that claim were real (`no known GPU vendor found in CDI specs`, `unresolvable CDI devices nvidia.com/gpu=all`) — but the conclusion named a **daemon limitation** where the cause is a **client-side default**: nerdctl resolves CDI client-side, and the *rootless* client's default spec dirs are `$XDG_CONFIG_HOME/cdi` and `$XDG_RUNTIME_DIR/cdi`, **not** `/etc/cdi` where `nvidia-ctk cdi generate` writes. Rootless NVIDIA access works once the spec is reachable from the rootless client's spec dirs. The control is the spec moved aside and restored: present → `NVIDIA GeForce RTX 4080 SUPER` (rc=0); absent → `unresolvable CDI devices` (rc=1); restored → rc=0 again. A doc that teaches a false prohibition costs an operator a capability they already have.
- **§14.2 — the CDI spec-dir rules were stated nowhere.** Later directories have higher priority; **equal priority is a conflict and the conflicting device is dropped** (not "last one wins") — measured, `CDI cache refresh failed: conflicting device`; `.json` and `.yaml` only, `.yml` is never opened; no recursion; a missing directory is skipped silently; `--cdi-spec-dirs` is comma-separated. The last point is load-bearing for the provider: a spec's *existence* is not a device's *availability*.
- **§14.2 — `enable_cdi` was removed in containerd v2.4** (`RELEASES.md:640`; the v1→v2 migration skips it), so a config that sets it teaches a key the daemon no longer reads. The commit-level provenance is in the issue: deprecation in v2.2, removal in v2.4, with `CDISpecDirs` surviving untouched. The same pickaxe shows containerd has **never** had a rootful/rootless CDI distinction — the split is nerdctl's, which is exactly what the spec now says.
- **§10 — CRIU's configuration surface was missing.** The precedence chain (`/etc/criu/default.conf` → `$HOME/.criu/default.conf` → `$CRIU_CONFIG_FILE` → `--config <file>` → CLI/RPC), the syntax (CLI options without `--`, one per line, **option and argument on the SAME line** — a split produces `Can't create log file --<path>`, which reads as a path error rather than a syntax error), `--no-default-config`, and the `/etc/criu/runc.conf` override. The content takes effect, proven with a control: the `org.criu.config` annotation creates the log file, and the no-annotation arm does not.
- **§10 — the NON-ROOT capability requirements were missing, and CRIU's own recommendation is insufficient.** CRIU's `Documentation/criu.txt` says `CAP_CHECKPOINT_RESTORE` "is the minimum that is required", and CRIU's own error message recommends `setcap cap_checkpoint_restore+eip`. **Neither is sufficient for the seccomp-suspend feature**: the kernel gates `PTRACE_O_SUSPEND_SECCOMP` on `capable(CAP_SYS_ADMIN)` = `ns_capable(&init_user_ns, cap)` — the **init** user namespace. Measured: with `cap_checkpoint_restore` CRIU's own capability gate *passes* and the run then dies at the *next* gate, `couldn't suspend seccomp`, **even in the init userns**. The spec states the correction with the source and files the CRIU-side divergence.
- **§10 — the pre-flight was undocumented, and the gates that existed were described by a form that is not a gate.** The pre-flight is `criu check --unprivileged --feature seccomp_suspend`: the **named** form short-circuits the check, so its exit status *is* the feature's result. The **bulk** form (`--extra`) is non-zero even on a host that checkpoints perfectly (unrelated Category 2 features are missing) — never a gate. `--unprivileged` is required, because without it CRIU fails earlier, in the mount namespace, with the same non-zero status. And the message is on **two different streams** depending on which gate fired (`pr_msg`→stdout for the capability gate, `pr_perror`→stderr for the ptrace gate), so a gate that reads one stream sees "no message" for half the failure modes.
- **§10 — the rootful instance is the one that checkpoints, and containerd prints the WRONG dump-log path for a rootless daemon.** The kernel's init-userns gate is the mechanism, and it is not fixable by any file capability: a capability lands in the *execing* namespace, which is the wrong one. The spec also records that the rootless daemon's CRIU log is readable only as root.
- **§10 — the removal ordering was missing.** `nerdctl checkpoint rm` validates the **container** argument, so a checkpoint must be removed **before** its container; afterwards the removal fails with `error removing checkpoint for container: <name>, no such container` and the directory stays in the data root, unreachable through nerdctl.

**`K3S.md`, `LIBKRUN.md`** — the D14 cross-references. Neither file mentioned CRIU, checkpoints, or rootless at all (measured: 0 matches in both), even though both inherit containerd's behavior from `CONTAINERD.md`. `K3S.md` gets the note that the `k8s.io` namespace is **rootful-only** (it exists only on the rootful daemon k3s shares) and that CRIU is a **nerdctl** surface the CRI plugin does not expose. `LIBKRUN.md` gets the note that a krun guest's **process** state is not checkpointable — **measured, not inferred**, with the mechanism (CRIU reaches the process and then fails at the *filesystem* stage, resolving the container root's fd against the **host's** mount table, `criu/files-reg.c:1790`) and a **crun control at rc=0** on the same host and image. Both point at the corrected `CONTAINERD.md` sections rather than restating them.

**One candidate was withdrawn by measurement rather than filed.** The plan's last open candidate claimed *"runc writes the CRIU image with mode `0o600`, so a rootless user cannot read back an image written by a rootful run"*. It is false in both halves: runc's only `0o600` file is `descriptors.json` (the **fd list**), while CRIU creates the image files at `CR_FD_PERM` = **0644** (`criu/include/crtools.h:11`) and runc creates the image **directory** at **0700** (`libcontainer/criu_linux.go:324`). Measured on the live host, with an absent-file control so that "denied" is distinguishable from "absent":

```
dir_mode=700  descriptors.json_mode=600  cgroup.img_mode=644

A: the NON-TRAVERSABLE dir (0700 root) — unpiped reads
  A1 read a 0644 image     -> rc=1
  A3 CONTROL: absent file  -> rc=1
B: the SAME files in a TRAVERSABLE dir (0755) — unpiped reads
  B1 read a 0644 image     -> rc=0
  B2 read the 0600 json    -> rc=1
  B3 CONTROL: absent file  -> rc=1
```

The image file's own 0644 mode never blocked a read (`B1` = 0); the **0700 directory** is the blocker. The implied fix — relaxing the image mode — would be a security regression, because `pages-1.img`/`core-1.img` hold a rootful container's process memory. A candidate that resolves to "the claim is false" is **withdrawn, not filed**, so no issue exists against `opencontainers/runc`.
