# 2026.294.0129 — docs(containerd): correct the CRIU restore, the runtime defaults, and the checkpoint store

## Summary

`CONTAINERD.md` §10 told a reader that a CRIU checkpoint can be restored under rootful
crun, and cited a measurement that does not reproduce. Live measurement on both deployed
hosts shows the restore works under **runc** and fails under **crun**, because containerd
invokes the OCI binary's `restore` with `-no-subreaper` and `crun restore` has no such
option.

This PR corrects that claim and six more divergences the same measurement produced, all
in `CONTAINERD.md`:

| # | Site | Was | Now |
|---|---|---|---|
| D1 | §10 | "Restoring works too — the restore continued at `tick-9`" | the measured truth, the mechanism, and the runc/crun A/B |
| D2 | §3.3.4 | "Five levels, all tested on the deployed hosts." | the five levels named, with the **process-state (CRIU)** level called out as a *separate* one outside both the five and the claim |
| D3 | §1.1 / §4.3 | the rootless rules stated, their *consequences* not | the silent rootless fallback on a permission-denied socket, and the rootless daemon's inability to allocate an ephemeral host port |
| D4 | §1 principle 2, §3.1, §3.2 | "The default runtime handlers never use runc" | the two-defaults split: the CRI plugin's default is crun (k3s); nerdctl's unqualified default handler is the daemon's own, and on these hosts it is **runc** |
| D5 | §10 | `nerdctl commit` described | a plain commit copies **no** labels, and `--change` accepts only `CMD`/`ENTRYPOINT` |
| D6 | §10 | the checkpoint-cleanup failure not described | the handler-split delete failure, the shim-kill remedy, and the fact that a containerd restart does **not** clear the task |
| D7 | §10 | "Checkpoint names are global to the containerd namespace" | a checkpoint is a **directory of CRIU image files** in the **nerdctl data root** — not a containerd object — and the scope is that data root, not the daemon |

The corrected text carries the *mechanism*, not just the retraction, so a reader who learns
"it does not work under crun" learns why and does not re-try it the same way.

### The two gate failures, and their RCA

The change-class gate failed twice before it passed. Both failures are recorded here
because R1 requires a fresh root-cause analysis for every failure, and a reader must not
have to hunt for it.

**Failure 1 — the worktree could not load the project.** The first `git commit` in this
session worktree was refused by the umbrella's own `pre-commit` hook:

```
charly: error: command "task": load project: .../opencharly/charly.yml: import charly ("./charly"):
  submodule "charly" is not initialized: .../opencharly/charly is empty, so
  .../opencharly/charly/charly.yml cannot be read; run: git submodule update --init charly
```

- **Mechanism.** The hook runs `charly task …`, which loads the project from the worktree
  root. A session worktree does not inherit the umbrella's initialized submodules, so the
  project loader cannot read an imported submodule's `charly.yml`.
- **Missed control.** The gate's own error message names the remedy, but nothing in the
  worktree-creation step surfaces it *before* the first commit. The control that was missing
  is the worktree bootstrap (see `## Filed issues`).
- **Blast radius.** The hook's `needs_charly` guard is read on only one of its two paths, so
  when a binary is found anywhere on the host the charly-backed assertions run
  unconditionally — and a fresh worktree is exactly the case the guard was written for.
- **Root fix.** Not in this change: it is the umbrella's worktree-bootstrap mechanics, a
  separate cutover, tracked as `opencharly/opencharly#498`. The remedy this PR's gate
  needed is the one its error message names, and it was applied.

**Failure 2 — the commit command could not be parsed.** A heredoc-form `git commit` was
refused by the pre-commit gate's command classifier:

```
pre-commit-gate BLOCKED: cannot parse this commit command; balance its quotes or use `git commit -F <file>`
```

- **Mechanism.** The classifier parses the *command line*, and the heredoc form's quoting
  is not something it can tokenize. The refusal names the supported form.
- **Missed control.** The classifier is a token-level check; a multi-line heredoc carrying
  prose with quotes inside it is indistinguishable from an unbalanced quote to that check.
  The supported form is `git commit -F <file>`.
- **Blast radius.** Any commit message with a quote character in it, written as a heredoc.
- **Root fix.** Applied: every commit in this PR uses `git commit -F <file>`, and the
  message file is the artifact that is reviewed. Not a defect in the umbrella — the gate
  told the truth about what it can parse.
