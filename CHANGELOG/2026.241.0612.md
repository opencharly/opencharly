# 2026.241.0612 — feat(claude): enable the development-scope charly plugins in the project config

## Summary of changes

The project's Claude Code config enabled only two charly plugins (`charly-internals`,
`charly-automation`), so 27 of the marketplace's charly skills loaded here and the rest —
including the `kind:` schema-authoring family the umbrella actually reads when reviewing
`charly.yml` shapes — did not. This enables the **development-scope** plugins: every
`charly-*` plugin EXCEPT the image/candy content families.

Concrete edits — `.claude/settings.json`, `enabledPlugins` only (8 keys added, nothing removed):

- `charly-image`, `charly-pod`, `charly-vm`, `charly-kubernetes`, `charly-local` — the `kind:`
  schema-authoring family (marketplace category `kind`)
- `charly-build`, `charly-check`, `charly-core` — the CLI-verb families (category `commands`)

The 16 image/candy families (`coder`, `jupyter`, `selkies`, `versa`, `distros`,
`infrastructure`, `tools`, `openclaw`, `ollama`, `hermes`, `immich`, `comfyui`, `openwebui`,
`filebrowser`, `agentteams`, `languages`) stay disabled. That line is deliberate and load-bearing:
**all four MCP-server-bearing plugins are image families**, so this change pulls in zero
plugin-provided MCP endpoints — no `charly` :18765, `jupyter` :8888, `chrome-devtools` :9224,
`marimo` :22718 or `airflow` :29999 attempting to connect with no box running here.

Side effect worth naming: `charly-internals:capabilities` cross-references `/charly-image:layer`
and `/charly-image:image`, which previously resolved to nothing in this project. Enabling
`charly-image` closes that dangling reference.
