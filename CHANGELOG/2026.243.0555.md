# 2026.243.0555 — fix(sync): the gitlink sync never opened a PR — its gate diffed the wrong thing

## Summary

**The daily gitlink sync has been running green and doing nothing.** Its change gate diffs the
wrong thing, so it reports "nothing to sync" precisely when it has work to do.

One line changed: `git diff --quiet` → `git diff --quiet HEAD`.

## Root cause

Two facts that are individually fine and fatal together:

| where | what |
|---|---|
| `scripts/sync-gitlinks.sh:33` | `git add "$path"` — every bumped gitlink is **staged** |
| `.github/workflows/sync.yml:30` | `if git diff --quiet` — compares **worktree against index** |

`git diff` with no revision does not look at the index against HEAD; it looks at the worktree
against the index. Since the script stages everything it changes, a *successful* sync leaves
nothing unstaged, the gate sets `changed=false`, and both the "Skip if a sync PR is already open"
and PR-creation steps are `if:`-gated off.

The automation is therefore a **no-op exactly when it has work**, and exits 0 either way — the
failure shape where a step reports success having done nothing. It is also why every gitlink sync
that has actually landed (`#66`, `#67`, `#68`) was opened by hand, against a rulebook that says the
fix for a stale pin *"is a sync (`task sync` + PR), not a hand-pin"*.

## How tested

**1. The live run that exposed it.** Run `33360266234`, dispatched 2026-08-31T05:21Z with three
repos demonstrably drifted. The "Bump pins" step computed the correct new pin:

```
== charly (default-branch HEAD) ==
  charly -> 0443e07
```

and the run still finished `success` with **no PR**, leaving the umbrella pinned at `1d0164f0`
while `charly`'s default-branch HEAD was `0443e073` — a straight policy-B violation
(README line 53: *"`charly` → its own default-branch HEAD (`main`)"*).

**2. The git semantics, reduced to a reproduction.** In a scratch repo, stage a modification, then:

```
git diff --quiet          -> exit 0    "nothing to sync"
git diff --cached --quiet -> exit 1    there IS a change
git diff --quiet HEAD     -> exit 1    there IS a change
git status --porcelain    -> "M  f"
```

**3. The fixed workflow, executed before merging.** `workflow_dispatch` can run a workflow from a
branch, so this was not left as a claim — run
[`33360774123`](https://github.com/opencharly/opencharly/actions/runs/33360774123) ran `sync.yml`
from `fix/sync-gate-diffs-wrong-thing`. **The gate now fires**: the run proceeded past the dirty
check and the already-open-PR check, all the way into the PR-creation step, which the old gate had
never reached. It then failed there:

```
Open sync PR: pull request create failed: GraphQL: GitHub Actions is not
permitted to create or approve pull requests (createPullRequest)
##[error]Process completed with exit code 1
```

That is a **second, independent defect this change exposed rather than caused** — and reaching it
is itself proof that the gate is fixed, because with `git diff --quiet` the job skipped that step
every time.

**4. End to end, after the second blocker was cleared.** With
`can_approve_pull_request_reviews` enabled, the same workflow was dispatched again from the same
branch — run
[`33361509708`](https://github.com/opencharly/opencharly/actions/runs/33361509708):

```
status=completed  conclusion=success
→ opened opencharly#75  "chore: sync gitlinks"  (branch sync/20260831-054851)
```

**That is the first sync PR this workflow has ever opened.** It carries the real drift, including
`charly` and `plugin-wl`, which had been stale on `main`.

## The second blocker — found here, cleared separately

The sync was disabled twice over: a gate that never fired, hiding a permission that was never
granted. Measured:

```
$ gh api repos/opencharly/opencharly/actions/permissions/workflow
{"default_workflow_permissions":"read","can_approve_pull_request_reviews":false}
$ gh api orgs/opencharly/actions/permissions/workflow
{"default_workflow_permissions":"read","can_approve_pull_request_reviews":false}
```

The workflow already declares `permissions: pull-requests: write`, so the job-level grant is not the
problem — the org/repo toggle *"Allow GitHub Actions to create and approve pull requests"* is off.

**The toggle is not flipped in this diff, on purpose** — it bundles *create* with *approve*, so
enabling it also lets any workflow approve pull requests, which against a repo that auto-merges on
a PASS verdict is a review-bypass surface. That is a security decision for a human, not a side
effect of a one-line CI fix. It was put to the maintainer explicitly and enabled org-wide by their
decision, as a separate settings change:

```
$ gh api orgs/opencharly/actions/permissions/workflow
{"default_workflow_permissions":"read","can_approve_pull_request_reviews":true}
```

(The umbrella repo carried its own override reading `false`, which shadows the org value, so it was
set at both levels.) The re-run above is what that unblocked.

Worth stating plainly: **even without the settings change this diff would be worth landing**, because
it turns a *silent* no-op into a *loud, actionable* failure. Before it, the sync reported success
while pins drifted; after it, it says exactly why it cannot proceed.

**4. The workflow still parses** — `yaml.safe_load` on the changed file.

## Why `HEAD` and not `--cached`

`git diff --cached --quiet` would also fix today's bug, but it would break the moment
`sync-gitlinks.sh` stopped staging — swapping one silent-disarm for its mirror image. Comparing
against `HEAD` sees staged and unstaged alike, so the gate stays correct regardless of what the
script does with the index. The comment added above the gate records both halves so the next reader
does not "simplify" it back.

### One consequence to note before merging

`#75` was produced by dispatching the workflow **from this branch**, so its sync branch was cut from
this branch and its diff contains this `sync.yml` change alongside the gitlink bumps. That makes it
a poor changelog for either concern. The clean sequence is: land this focused PR first, then
re-dispatch from `main` so the next sync PR is gitlinks only — and close `#75` rather than merge it.
Noted here so a reviewer does not read the overlap as an accident.
