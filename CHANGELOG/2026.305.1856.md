# 2026.305.1856 — fix(hooks): refuse a commit made on the default branch (charly#842)

## Summary

A `git commit` made while `HEAD` is the checked-out default branch is invisible to every gate the org has: the clone-level hook guards pushes (`hooks/pre-push`), and the org ruleset only governs what reaches the remote. `opencharly/charly#842` records the class, observed after a `&`-backgrounded chain was killed mid-hook and the re-run committed on `main`.

This lands remedy ① from that issue — the commit-time guard — and nothing else.

| file | change |
|---|---|
| `scripts/check-default-branch.mjs` | new: refuse a commit when `HEAD` is the default branch, and name the remedy |
| `hooks/pre-commit` | run the guard FIRST, before the change-class legs; the header now describes three parts instead of two |

The guard is deliberately narrower than "never commit on main": it refuses only when `HEAD` is a symbolic ref pointing at the default branch, so a detached HEAD (a rebase, a bisect, a read-only checkout) is left alone. The default branch is read from the `origin/HEAD` symref, falling back to the conventional `main` only when the clone has no such symref, so a repo whose default branch is `trunk` refuses on `trunk`.

It is placed first because every other leg judges the DIFF and none of them can see which branch the commit lands on, and because it needs no charly binary, no project and no submodule — so it runs even where the rest is skipped. That is exactly the state this fix sat in: `opencharly/opencharly#513` and `opencharly/opencharly#498` made every commit in a fresh worktree fail on an uninitialized submodule, and both are now closed.

It does not replace the remote default-branch audit in `charly task verify`: that one reads `git ls-remote` state no commit can change, and answers a different question.
