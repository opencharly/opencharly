### 1. `repo-setup` — the checklist was WRONG about how a repo is created

The old step 1 said "Create `opencharly/<name>` (non-fork; it must end up on default branch `main`)",
and step 2 told the author to add the `tag-on-merge.yml` caller. Neither survives contact with the
org ruleset:

- the **`creation`** rule makes the first `main` impossible by `git push`, by the contents API, by
  `auto_init` (which leaves the repo with no refs) and by a branch rename — all four measured with
  their exact errors in `opencharly/.github`'s own `bootstrap-repo-main.sh`;
- the only actor that can create that ref is the `charly-auto-merge` App, and
  `bootstrap-repo-main.yml` mints exactly that token for it;
- that workflow also **installs and asserts** the per-repo caller, so hand-adding it lands a byte-wise
  modification of a file the org owns.

The checklist now carries the measured order — create EMPTY, push ONE throwaway seed branch, dispatch
the bootstrap, then PATCH the three settings the App cannot set (`default_branch`, `allow_auto_merge`,
`delete_branch_on_merge`) — plus the umbrella leg corrected: `git submodule add` writes no `branch =`,
so the pin's INTENT must be declared in the same commit, and the pin must not be advanced with the
org-wide `charly task sync` wave.

### 2. `git-workflow` — a new section: "The ARMED-AND-SILENT stall"

The POISON class has a non-passing run on the head. This sibling has **none**: armed
(`autoMergeRequest` present), every same-name run `success`, `mergeStateStatus: CLEAN`, base current —
and no merge. Measured on `opencharly/sdk#591` (armed 15:35:21Z, still open well past the org's own
measured 7m41s PASS→merge bound) against `opencharly/opencharly#1168`, armed by the **same**
`github-actions[bot]` minutes earlier and merged **8 seconds** later — so the arming identity is not
the variable and "it is just slow" does not explain it.

The section carries the one-call diagnostic that separates the two classes
(`check-runs?filter=all` — all `success` ⇒ this class, nothing to re-run), the cure (ONE empty
re-trigger commit: a `synchronize` event is the only type the org required workflow acts on, and an
empty commit moves the HEAD and not the TREE so tree-keyed claims survive), the body re-keying that the
new head requires, and "do it ONCE — a second stall is a platform anomaly, escalate with both timings
and consider filing it, because the org's stalled-automerge detector covers three shapes and this is a
fourth".

### 3. `git-workflow/references/pin-intent-and-currency` — a submodule is BORN `unpinned`

`git submodule add` writes `path` and `url` and nothing else, so the new path has no intent and
`charly task verify` fails **structurally** (`pod-strata: no intent and no branch= in .gitmodules —
declare one`) until the same commit declares it:

```sh
git submodule add <url> <path>
git config -f .gitmodules submodule.<path>.branch main
```

Cheap to forget, because `submodule add` reports success — measured on the umbrella commit that added
`pod-strata`: gitlink, `.gitmodules`, `import:` and README row all correct, and the gate still failed
on that one line.

### 4. `git-workflow/references/umbrella-mechanics` — a linked worktree's gate judges what it can READ

`scripts/design-cite.sh` resolves every citation into a pinned module **at that pin** and FAILS when
the module store does not hold the commit: *"the control cannot judge a pin it cannot read"*. A session
worktree materializes only the derived working set while the gate judges the whole declared path set,
so the first push can be blocked by an absence that is not a defect in the change. The remedy is the
one the message prints (`git submodule update --init <the paths it names>`), and the distinction worth
knowing: **an unmaterialized checkout is a NOTICE for the currency question and a FAILURE for a
citation control** — the difference is whether the control must read the pinned bytes.

already correct in `/charly-internals:cutover-policy`; these edits cite that section rather than copy
it (R2).
