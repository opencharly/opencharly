## Why the CI gate was deleted (T4 — guardrail change, explicit justification)

**This is a deliberate weakening, requested by the maintainer after being shown the audit and the trade-off. It is not incidental.** What is lost is stated plainly at the end of this section.

Judged against the `README.md` contract — the umbrella is *"a **view** of the org, not a new home for anything"*, and no workflow builds, deploys, publishes or releases:

| Assertion in `verify` | What it prevents | Verdict |
|---|---|---|
| `[ -d $path ]`, clean tree, `gitlink == HEAD`, charly's nested init | nothing — `actions/checkout` **creates** this state; can only fail if checkout already failed, which already fails the job | empty in CI |
| `.gitmodules` `url=`/`branch=`, `>=20` modules | nothing — a malformed entry fails the checkout step itself | empty in CI |
| `branch=` equals real remote default (344 `ls-remote`, 163 s) | an upstream branch rename. No PR diff can cause it; `sync-gitlinks.sh`, its only consumer, fails on its own if stale | empty as a PR gate |
| **policy B**, **`umbrella-gates.ts` parses**, **harness parity** | the only assertions a commit can violate | **real — kept, and moved to `hooks/pre-commit`** |

Empirically confirmed rather than argued: on a clean tree `git submodule status | grep -cE '^[+U]'` is `0`, and `pod-chrome-cdp` passes the clean-tree and `gitlink == HEAD` assertions while its own nested `charly` is uninitialized.

`smoke` is separately redundant (R3): `charly/go.work` has one member (`use ./charly`), every candy resolves from the Go proxy at a pinned `go.mod` require, and **charly's own `ci.yml` already runs `go test ./charly/...` + `gofmt`** on those commits. It re-tested a snapshot charly had already tested.

**What is genuinely lost, stated without hedging:** server-side enforcement. `hooks/pre-commit` is per-clone (needs `task hooks` once), and `--no-verify` bypasses it for a human at a terminal — the harness gates still block that for agents. A contributor who never installs it gets no gating. After this, `validate` is the only thing running on the server. The full pinning audit is demoted to on-demand `task verify`; it is still load-bearing there, proven below. The maintainer accepted this trade-off explicitly.
