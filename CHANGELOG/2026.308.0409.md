# 2026.308.0409 — docs(design): record what the design retires, and why (batch 7)

## Summary

Batch 7 of the DESIGN amendments the capability ledger records (tracked in #838). Eight capabilities
carry `accept retirement` in the ledger, and until now that decision lived **only in the ledger's own
cells** — a reader had to trust a row that said "retired" without the document ever saying so.

**A.9 is that record.** It names each retired capability, the rule that retires it, and the count that
makes it dead:

| capability | retired by |
|---|---|
| kind:agent-team | D-KIND-1 — the first-party kind set is closed; a team is a workload the cluster kind carries |
| kind:desktopentry | D-IR-4 — a `file:` entry has exactly one effect |
| kind:displaymanager | D-IR-4 with `service:` — a service names one unit's exec and user |
| kind:session | D-IR-4 — files and a service, not a node |
| kind:theme | D-IR-4 — a `file:` writes literal bytes |
| verb:file-parity, verb:module-pins, verb:splice-region | D-LAW-2 — retired with zero authored uses |

Every one measures **0 of 148 authored manifests**, by grepping every authored `.yml`/`.yaml` outside
`CHANGELOG/`, `docs/` and generated `.build/` trees. A.8 now points at A.9, and the eight rows cite
`DESIGN.md:§A.9`, so the decision is checkable from the ledger rather than asserted by it.

A.9 also states the boundary it does **not** cover: a deliberate narrowing that routes an operation
elsewhere rather than dropping it — `D-VERB-6`'s `api`-method rule for vendor-internal operations —
is the requirement's own business, not a retirement, and its rows name the requirement.

| file | what changed |
|---|---|
| `DESIGN.md` | the new A.9, and A.8's pointer to it |
| `design/dulling.tsv` | the eight retirement rows cite `DESIGN.md:§A.9` |
