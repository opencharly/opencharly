# 2026.278.2215 — fix(reasonix): the ollama-websearch sidecar must answer the host's InitializeResult

# reasonix: fix the boot-blocking handshake and the skill-root warnings

## Summary

Two defects, one cutover. `reasonix` could not start **at all**, and once it could, it
printed ~3,500 warnings on every boot. Closes #380.

### 1. Boot-blocking handshake (fixed in `69d8357`)

Every reasonix session aborted at boot:

```
$ reasonix -p "hi"
error: boot: required extension runtime "ollama-websearch" failed to start: extension sidecar startup handshake failed after 25ms: invalid initialize result: params.name is required
$ echo $?
1
```

`reasonix doctor --json` was healthy — only boot failed, because the plugin manifest declares
`runtime.required: true`, so the failing handshake aborts the whole runtime.

**Root cause (MEASURED, installed reasonix v2.28.0).** `.reasonix/plugin/sidecar.py`
answered `extension/initialize` with a result authored from the *upstream* protocol docs,
never from the **installed** host's registered `protocol.InitializeResult`. The host decodes
that DTO strictly, and the reply diverged three independent ways:

| Field | Host requirement (measured) | Sidecar sent |
|---|---|---|
| `name` | **required** string | absent |
| `version` | **required** string | absent |
| `stateSchemaVersion` | **required** int (`min=0`) | absent |
| `protocolVersion` | **required**, value `"2"` | `"reasonix.extension.v2"` |
| `capabilities` | **not a registered field** | `["tools"]` |
| `tools` | optional, array of **strings** | `["web_search","web_fetch"]` |

Measured drop tests: omit `name` → `params.name is required`; omit `version` →
`params.version is required`; omit `stateSchemaVersion` → `params.**** is required` (name
redacted by the credential pass; `0` accepted); `protocolVersion:"3"` → `The peer's extension
protocol version is not supported.`; `protocolVersion:2` (int) → `params do not match the
registered type`; any unknown field → `params do not match the registered type`.

### 2. Skill-root warnings (fixed in `f548a4c`)

Even after boot succeeded, every launch printed ~3,501 warning lines. `[skills] paths =
["marketplace"]` pointed at the marketplace **family** root, but reasonix expects a
multi-**skill** root, so it scanned family prose as skills. MEASURED (reasonix v2.28.0): 389
files warned `skill.missing_description` — 3,447 of them `marketplace/CHANGELOG/*.md`, plus
the root `AGENTS.md` / `DISPATCHER.md` / `README.md` and two family READMEs. reasonix's own
default scan is clean; the noise was entirely our path entry.

`paths` now lists the **40 directories that actually hold skills** — every
`<family>/skills/` (each a `<skill>/SKILL.md`) plus the two `<family>/agents/` roster dirs
(hand-authored `<agent>.md`, loaded as skills). Result: **zero boot warnings**, the **same
362 skills**, **none lost**. (The 3 dropped entries were the prose false-positives.)

### Review findings on the first head (`69d8357` → fixed in `f548a4c`)

The `charly/pr-validator` returned BLOCK on head `69d8357` with two findings, both fixed:

1. **R1 doc/reality divergence.** `handle_initialize`'s docstring claimed the bare
   `params.tools` fallback was "for the offline/direct invocation documented in README.md",
   but this PR had changed that README recipe to send `params.manifest.tools`. The comment now
   states the truth: the fallback tolerates a direct invocation that omits the wrapper (the
   unit tests drive the handler both ways).
2. **R3/R5 dead constant.** `PROTOCOL_ID` was renamed from the old `PROTOCOL_VERSION` but
   nothing read it (the reply uses the new `PROTOCOL_VERSION = "2"`). Removed.
