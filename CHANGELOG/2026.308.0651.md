# 2026.308.0651 — feat(design): let a builder name several managers, as authors do (batch 10)

## Summary

Batch 10 of the DESIGN amendments the capability ledger records (tracked in #838). The authored shape
of a builder is a **map** of manager word to the box that provides it — 76 builder nodes measured
across the tree, every one keyed by `aur`, `cargo`, `npm`, `pixi` or `mise` — while the design allowed
one `{name, box}` payload per node. A box that builds through four managers had to become four nodes.

`#BuilderManager` is now that map: `builder: {manager: {pixi: box, mise: box}}`.

- The typed-kinds example uses it (the `mise-env` builder names both `mise` and `pixi`);
- the **D-VAL-2 rule follows it** — every manager entry must resolve to a box, not a candy;
- the negative case that exercised the old field path now exercises the new one.

`kind:builder` becomes `sharp` on the measured reading: the plugin's internal 19-field template is not
a surface authors write, and D-LAW-8 already says a builder plugin is a manager row rather than a
plugin of its own.

| file | what changed |
|---|---|
| `DESIGN.cue` | `#BuilderManager` is a map of manager word to box |
| `DESIGN.md` | the builder example uses the map form |
| `design/example/rules.cue` | the D-VAL-2 rule checks every manager entry, and the bootstrap arm separately |
| `design/negative/builder-box-candy.yaml` | exercises the map entry instead of the old field |
| `design/dulling.tsv` | `kind:builder` becomes sharp |
