## Summary

Head `f7fed5f6470003f47a1f2e484712c7d4385c8840` — 6 files changed, 555 insertions(+), 14 deletions(-).

**The umbrella's own committed prose, and the tree it lives in, disagreed — and the disagreement was load-bearing.** Three claims in this repo were false: what BLOCKS a landing, the order the org's release machinery runs in, and the module version the repo's own scripts cite. All three are one class of defect: **a mechanism or a version stated from memory instead of derived from the thing that owns it, with no control that re-derives it.** The control written to keep the third class true then found a **fourth** defect — in itself.

**Finding 1 — the skill said the CHANGELOG entry lands in the tagged tree. It does not.** The org's `tag-on-merge` workflow creates the tag **AT** `pr.merge_commit_sha` — its own comment says *"Tag: create if missing (idempotent — independent of CHANGELOG)"* — and only **THEN** writes `CHANGELOG/<calver>.md` from the merged PR's title + body on `main`, which lands as the dispatcher's own follow-up commit `docs: add CHANGELOG <calver> for PR #<n>`. The tag is created before the entry exists, so the entry can never be in the tagged tree. MEASURED, two repos:

```

ABSENT from the tagged tree
$ git log --oneline -2 origin/main
e5f90075 docs: add CHANGELOG 2026.298.0740 for PR #184
dd289db1 fix(ci): bound every job and step in this repo's workflows ... (#184)

$ git show v2026.298.0430:CHANGELOG/2026.298.0430.md      # opencharly/opencharly

```

The claim is load-bearing: *"block on what gets TAGGED"* decides what stops a landing, and it sent a reader to a file the tag does not contain. The corrected text says what survives the merge (the PR body and the entry, both durable on `main`) and what the squash replaces (the intermediate commit messages), and it names the order with the measurement inline.

**Finding 2 — the same skill described that order backwards.** `references/validator-and-calver.md` said *"after the squash merge, write `CHANGELOG/$VER.md` on `main` … ; **then** tag the merged HEAD"*. The workflow tags FIRST, at the merge commit; "the merged HEAD" after the changelog write is the dispatcher's own commit, and no such tag exists. The corrected bullet states the workflow's real order, and says why the order is the point: the tagged tree is the merge commit, and the entry arrives in the commit after it.

**Finding 3 — two prose citations of a plugin-task version the pinned charly falsifies.** `scripts/sync-pr-body.sh` named a version five releases behind the pin and `charly.yml` named one twenty-nine days behind it, while this repo's pinned charly (gitlink `f1f85d19`) has `charly/go.mod:141` requiring a third. The three source line numbers the script cites (`verbs.go:736`, `cli.go:261`, `cli.go:210`) are CORRECT at the pinned version — only the version strings were false, and only the version strings are changed.

**The root fix is a control, not a patch.** A version transcribed into prose is a copy of a fact whose owner (the charly pin) moves on every release, and nothing re-read it: a charly pin bump changes the version the prose names, and no gate said so. `scripts/check-cited-plugin-task-version.mjs` re-derives the version from the **pinned** charly's own `go.mod` and fails when any plugin-task version this repo's own prose cites differs — so the pin advancing turns the gate RED at exactly the moment the citations beside it must be re-read.

**Finding 4 — the control read the wrong copy, and the first commit of this change proved it.** A commit ships the **INDEX**; the gate read the **working tree**. A file STAGED with a stale citation and then fixed in the worktree read GREEN, and the commit shipped the stale copy. That is not hypothetical — the first commit of this change was made exactly that way (the file was edited after it was staged), and the tree it would have shipped carried the very literals the gate had already been shown to flag. The fix is which tree the gate judges: **for every file where the worktree and the index disagree, the index's copy is judged** — the copy a commit ships — and the worktree's copy where the two are identical, where the worktree *is* the index.

**Two of the four findings were introduced by this change, and both are fixed here.** The control first fired on **its own source** (its docstring quoted the two stale literals, and its mutations wrote versions of their own) — a control that holds a copy of the fact it checks rots exactly like the prose it polices, so every version it needs is now **derived** from the pin, and the file quotes none. It then read the wrong copy, as above.

**The table is the diff's own file set** — the umbrella's own `scripts/check-pr-body-diff.mjs` reconciles it against the diff on every push: a path the diff changes and the table omits, or a path the table lists and the diff does not change, blocks the push.
