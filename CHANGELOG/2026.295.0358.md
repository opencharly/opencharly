# 2026.295.0358 — feat(coord): rename BLOCKS/UNBLOCKS to WAITING/HOLDING/CLEARED, and gate the closed set (opencharly/opencharly#567)

## Summary

This is the umbrella's leg of the coordination-verb cutover
(`opencharly/opencharly#567`). The producers have landed — `opencharly/action-review#22`,
`opencharly/layer-charly-internals#130`, `opencharly/layer-charly-internals-extra#29`,
`opencharly/marketplace#526` and its follow-up `#528` — so the corpus the umbrella
vendors now states one grammar, and this PR makes the umbrella state the SAME grammar
and **proves** that the two agree.

Head: `5af20c4864967b731bbdf47defa867b849fe22b7` on `feat/coord-verb-rename`.

The closed set is now nine labels, and it shares **no** token with the validator's
verdict vocabulary:

```
CLAIM · OWNING · HANDING OVER · TAKING OVER · WAITING · HOLDING · CLEARED · STATUS · RESOLVED
```

`BLOCKS` was the collision: in the validator's rulebook it meant *this finding blocks the
merge*, and in a coordination comment it meant *I am blocked*. The same file carried both
meanings, so a coordination comment announcing a dependency read like a verdict rejecting
a PR. `BLOCKS` is now `WAITING` (the blocked side) or `HOLDING` (the blocking side) —
two verbs, so the first line states which side speaks — and `UNBLOCKS` is `CLEARED`. The
validator's own `BLOCK` verdict is untouched.

**The umbrella's own copies of the set** — `AGENTS.md` (Part II #7's grammar rule, the
COORD row of *"What the validator checks"*, the *"Answer coordination first"* rule, the
session-ledger line, and Part II #11's *"say so the moment you block someone"*), the pi
harness prompt `.pi/APPEND_SYSTEM.md`, and the opencode plugin
`.opencode/plugins/coord.ts` (both copies it holds: the `VERBS` array and the
hand-written tool description) — now carry the nine labels.

**The new gate** `scripts/check-coord-verb-set.mjs` compares every copy mechanically, in
two jobs: every surface that ENUMERATES the set is extracted, parsed in order, and
compared against the canonical nine (same labels, same order); and every place that
STATES the set is COVERED by a surface, so a copy nobody listed turns the gate RED. The
second job exists because the marketplace's `scripts/coord.sh` stated the set THREE times
while every assertion compared the two copies somebody had named — the third copy
drifted silently, and it was found by reading, not by a test. The canonical list lives
in the gate and is not derived from any copy: a copy that drifts is a finding, not the
new truth.

**The gates behind the tooling** were widened with the rename, because they asserted
nothing about the new verbs: `scripts/check-opencode-coord.mjs` now asserts the `VERBS`
array IS the nine-label closed set in order, that `canonicalVerb` normalises the three
new labels, that it **rejects** the retired `BLOCKS`/`UNBLOCKS`, and it compares the
shell's comment output against the TypeScript's byte-for-byte for `WAITING`, `HOLDING`
and `CLEARED` as well. `scripts/check-issue-tracker.mjs` carries a `WAITING` fixture, so
the tracker's `parseVerb` path reads the new grammar and the LATEST coordination comment
still wins.

**The four gitlinks** (`action-review`, `layer-charly-internals`,
`layer-charly-internals-extra`, `marketplace`) carry the corpus that carries the same
nine labels, so the umbrella's own gate compares the umbrella against a corpus that
states the same set.

**The pins this PR does NOT carry.** The four gitlinks were advanced by the sanctioned
path — `charly task sync` (the pin verb's `MODE=bump`) in this session's own worktree,
which reported `2 step(s), 0 failed`. That verb is org-wide: it also rolled twelve gitlinks
that belong to **other** sessions' waves — `charly`, the five `distro-*` edges,
`layer-omarchy-base`, `layer-omarchy-shell`, `layer-openclaw`, `plugin-marketplace`,
`plugin-migrate` and `sdk` — and the same run confirmed that
`opencharly/opencharly#571` and `#572` are in flight for exactly those hops. Those
twelve were un-staged and their checkouts restored to the gitlinks `HEAD` records, so
this PR carries the four repos of this cutover and nothing else, and the umbrella's
checkout audit stays green. This is the `#562` precedent, applied in the same direction.

**Why this is ONE PR and not the two the plan named.** The plan split the umbrella into
a prose PR and a pins PR for one reason: the umbrella's `marketplace` gitlink may only
point at a MERGED marketplace commit, and marketplace had not merged when the plan was
written. It has now (twice), so the split's reason is gone — and the split would have
been a WINDOW, not a safety: for the length of the split, the umbrella's own rulebook
would state a set the corpus it vendors did not, which is precisely the divergence the
new gate exists to make RED. One PR closes that window by construction. The scope is
the union of the two planned PRs; nothing is narrowed, deferred, or left out.
