# 2026.279.1739 — fix(harness): an arm generation guards the watch binding exit handling (WATCHER FATAL with empty stderr)

## Summary

Twice this session the wake channel died with

```
WATCHER FATAL — the GitHub watcher failed 3 times immediately; last stderr: (none)
```

after a `watch_arm action=restart` — and afterwards `status` reported `armed: no` while a watcher was genuinely running and holding the lock. This is the RCA, the fix, and the live A/B that proves it.

## Mechanism

`armGh()`'s exit handler was **not generation-scoped**, so an **already-stopped child's exit mutated the current arm's state**:

```ts
proc.on("exit", (code) => {
  gh.proc = null;                                    // ← cleared the LIVE arm's slot
  const fast = Date.now() - gh.startedAt < 5000 && !sawLine;   // ← measured the NEW arm's start
  gh.fastFailures = fast ? gh.fastFailures + 1 : 0;  // ← counted its own deliberate SIGTERM
  if (gh.fastFailures >= 3) { deliver(FATAL…); return; }       // ← stops re-arming for good
  gh.rearmTimer = setTimeout(() => armGh(pi), fast ? 15000 : 2000);   // ← spawns a DUPLICATE
});
```

`restartGh` kills the running arm with `SIGTERM`, then arms its successor. The killed child's exit then arrived **after** the successor was installed: it cleared the tracked slot, scored a "fast failure", and scheduled a **duplicate** arm — whose `watch_lock --takeover` TERMed the live watcher, which exits **silently** (code 143: no stdout, no stderr) → another fast failure → 15 s later another duplicate → three of those and the binding gave up permanently, while a stray kept holding the lock.

**The empty stderr is the fingerprint.** It is what rules out the obvious suspect: the lock-loser path is not silent — `watch_lock_or_exit` prints `could not acquire the watch lock` to stderr and exits **6**, and the extension's terminal branch is 5/7. A silent 143 is an externally TERMed child.

## Live A/B, on the real binding

**OLD code** (measured before the fix): a restart produced **two concurrent arms**, a churning lock holder `587412 → 587777 → 588867` within a minute, and the FATAL twice.

**FIXED code** (a session armed at `session_start`, then two restarts, kept alive through an observation window):

```
[T+10s] real watchers:  pid=598912 ppid=597781 age=00:04   holder: … 598912
[T+30s] real watchers:  pid=598912 ppid=597781 age=00:24   holder: … 598912
[T+50s] real watchers:  pid=598912 ppid=597781 age=00:44   holder: … 598912
```

Same pid throughout, one arm at a time, **no duplicate, no churn, no FATAL** — and `status` reported `armed: yes (this session's arm is tracked)`.

## What changed

- **`gh.gen` arm generation** — the stdout/stderr/exit handlers ignore a SUPERSEDED arm, so a deliberate stop is never a failure and never re-arms a duplicate.
- **The tracked slot is cleared only for its own child** (`if (gh.proc === proc)`), never by a stale arm.
- **`restartGh` supersedes BEFORE killing.** Load-bearing, not decorative: `armGh` can return *without arming* (every item already terminal), so without the bump the killed child's exit would still match the current generation.
- **Exit 6 is a peer, not a failure** — another watcher holds the lock; a note plus a 60 s backoff, never a fast failure and never a FATAL.
- **`status` says what it actually tracks** (`yes (this session's arm is tracked)` / `no — this session tracks no arm`).

## Follow-up (marketplace-side, measured here)

Two holders coexisted during the A/B (`…594550` for the main checkout, `…598912` for the worktree-rooted session) because `watch_key` hashes **argv0 — the script's absolute path** — together with the args. So the same scope watched from a worktree-rooted session gets a *different lock* than from the umbrella root, i.e. **two watchers on one scope = duplicate wakes**, and one stale `charly-watch-*.lock`/`.pid` per distinct path/args over time (16 present here). The remedy — a path-independent key (item list + events, not the script path) and stale-file hygiene — belongs in `marketplace/scripts/_watch_common.sh`, so it is a cross-repo cutover, tracked in #408 alongside this fix's own accounting work.
