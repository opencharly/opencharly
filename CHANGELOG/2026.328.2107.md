# 2026.328.2107 — docs(rulebook): no charly pod runs as container root

## Summary

The rulebook never said what a pod's user namespace may be, so the emitter was free to invent one — and it did: a deployment carrying the CDI GPU device *and* a host-owned bind mount was rendered `UserNS=host` with `User=0:0`, a container-root workload. D-HW-10 already forbids that: a deployment is rootless unless its stack declares `privilege: rootful`, and a bind mount is not such a need.

Part I now states the rule, in the same gist-plus-owner form as its neighbours:

- **No charly pod runs as container root.** A unit with a bind mount runs as the image user under `UserNS=keep-id:uid=<uid>,gid=<gid>` — under keep-id that user is the invoking host user, so a host-owned bind or a gocryptfs plaintext directory is writable as-is, with no chown.
- **The GPU stays a CDI device** on every GPU unit. What keep-id rejects is a CDI spec's `mounts` (crun `mount_setattr … EPERM`, exit 126), never the device — so the deployment points the engine at a derived **devices-only** spec (`deviceNodes` only, `--cdi-spec-dir`) and binds the driver libraries read-only to their SONAME paths.
- `userns=host` with `User=0:0` is a blocking defect wherever it appears, and `HOME`/`XDG_*` are never pinned to compensate for it.

The detail stays in the owning repos: `/charly-distros:cdi` (the measured matrix and the kernel reason), `/charly-automation:enc` (`-allow_other` and its cost), `/charly-internals:xdg` (HOME inside a pod).
