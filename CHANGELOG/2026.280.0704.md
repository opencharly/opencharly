# 2026.280.0704 — fix(pi): a STALL is a STATE fire — the watch binding must not re-arm (hot loop)

## Summary

The pi watch binding hot-loops on a **stale** watch item. `gh_watch.sh` deliberately sets `WATCH_DONE=1` on every **STATE** fire (`MERGED`/`CLOSED`/`STALL`) and does **not** re-arm — its own comment (`marketplace/scripts/gh_watch.sh:345-347,380`):

> *"A STATE fire (merged/closed/stall) sets `WATCH_DONE=1` and does NOT re-arm: the successor would IMMEDIATELY re-fire it (a merged PR stays merged; a stalled item stays stalled), which would livelock and burn the API budget."*

The extension uses `--no-rearm` and re-arms itself. `MERGED`/`CLOSED` land in its `done` set, so `active` empties and it correctly stops — but **`STALL` did not**, so the extension's own re-arm bypassed the script's guard and re-armed every 2s.

MEASURED (stale item, right after `watch_arm restart`, sampling the process count every 2s):

```
t+00s procs=1   t+02s procs=0   t+04s procs=2   t+06s procs=0
t+08s procs=3   t+10s procs=0   t+12s procs=0   t+14s procs=3   t+16s procs=0   t+18s procs=3
```

`arm -> STALL -> exit 0 -> re-arm(2s) -> ...` — an API call per cycle, and the extension's STATE-dedupe suppresses the *delivery*, so this burns budget silently.

**The fix (2 commits):**
1. `957638d` — mark a `STALL`ed item and exclude it from the re-arm set (mirroring `WATCH_DONE`); clear on `restart`; report it in `watch_arm` status. Also `armed` now reports `re-arm pending` when a timer is set (it previously read `no` at any moment between a one-shot child's exit and its re-arm).
2. `9640b38` — **finding 1 of the prior review, fixed:** that guard makes the pre-existing `gh.stall` delivery-dedup unreachable (a stalled item is never re-armed, so it can never emit a second STALL). The dead map and its now-false comment are **removed** (R3/R5).
